# internal/proxy

The network policy proxy: one process per VM, on every [network tier](../../docs/content/docs/internals/network.md), on the host, run as `devvm _proxy`. Go, standard library only, with `internal/daemon`, devvm's background-process helper, and `internal/safefile`, devvm's reader of files a VM can write, which are standard library only too (depguard enforces all three).

The VM can reach nothing but this proxy. On macOS its Lima hostagent runs under a Seatbelt profile, and on Linux QEMU's network is restricted. Other programs on the host can reach the port too, so the port alone doesn't identify the VM. Every request must carry the VM's password in `Proxy-Authorization`, with the user `devvm`, and the VM's proxy URL has it. The VM's placeholders end in a random value of its own, which isn't the password, so no other VM's or program's placeholder gets a secret. The proxy runs with one config, `Config`, which holds the password, and it refuses to start without one ([how devvm runs it](#how-devvm-runs-it)). For each connection it:

- answers `407` without the VM's password;
- takes only a host name with no empty label, after it lowercases the name, in ASCII alone, and drops one trailing dot, or an address, and answers `400` to anything else, a name with a character that isn't printable ASCII included, which it never folds into ASCII (the Kelvin sign into `k`);
- refuses `devvm.proxy`, its own domain, and every name under it with `403`, logged as a refused block, before the links, the policy or a company proxy see it: only an absolute-form request for `http://devvm.proxy/` reaches its endpoints, and `CONNECT devvm.proxy:P` has none; it refuses the stand-in address `198.18.0.1` (`SentinelAddr`) the same way, with a reason that says the tool resolved the name itself;
- takes `CONNECT transparent.devvm.proxy:PORT` (`TransparentHost`), which a confined VM's `devvm-transparent` sends for a tool that skipped the proxy settings, after the password and the tunnel slot and before anything else: the host is the TLS ClientHello's SNI or each HTTP request's `Host`, read from the first bytes within 10 seconds, and the connection is then judged and carried as `CONNECT host:PORT` is (`routeFor`), its events with `"via": "dns"`; a blocked TLS host gets a certificate for it from the VM's CA and the `403` text, and `GET http://devvm.proxy/transparent/ports` lists the ports to redirect (`transparentPorts`) ([transparent mode](../../docs/content/docs/internals/network.md#tools-that-skip-the-proxy));
- with `links` in its config, sends a request for one of the VM's links (`CONNECT db:5432`, `GET http://db:5432/`) to that link's socket on the host before any rule (below);
- checks `CONNECT host:port` and absolute-form requests (`GET http://host/…`) against the VM's policy, which is devvm's built-in policies, read from the binary, and then the user's policy files, and tunnels or forwards allowed ones untouched;
- resolves names itself, and refuses the host's own addresses and internal ones (loopback, private, link-local, multicast, unspecified, CGNAT `100.64.0.0/10`) unless a rule names the address; through a company proxy (`upstream`), which resolves names itself, it refuses a name when the host's resolver answers with such an address, and a name the host can't resolve when only `**` allows it (unless `upstream_unresolved`, which builds on Lima get), and it reads at most 64 KiB of the company proxy's answer to `CONNECT`;
- requires a TLS ClientHello in a tunnel to name the CONNECT host (SNI), in ASCII, letters' case aside, whole in one record of at most 16 KiB and 256 bytes (`helloRecordMax`) within 10 seconds of its first byte (`helloTimeout`), and passes nothing the VM sends to the far end before it has checked it, while the far end's bytes reach the VM at once, so a server that speaks first, such as SMTP's, sends its greeting before the VM sends anything; a stream whose first byte starts a TLS record is TLS from then on, so a record header that never comes whole, or a ClientHello that doesn't parse in its one record, is refused, never passed on, an address's tunnel's included, which may have no name;
- for a host whose rules narrow it to some methods or paths (`api.github.com GET,HEAD /repos/`), judges each of its requests, every one on a kept-alive or HTTP/2 connection, with one matcher (`match` in `request.go`), decrypting its `:443` tunnels with the VM's CA and refusing them on other ports (`hostRules.byRequest`, `server.judgeRequest`), and answers `403` to a request the rules refuse, logged with its method and path;
- for hosts with a bound secret, swaps the placeholder in one header for the real value: it intercepts their `:443` tunnels, and does the same for absolute-form `https://` requests (everything else passes unread), with certificates from the VM's CA, of which it keeps the 1024 used most recently (`leafCacheMax`);
- for an agent's OAuth token endpoint (`captures`), intercepts its host's `:443` tunnels the same way, and hands a `POST` to its path, at most 64 KiB, and its successful reply, at most 1 MiB, to `IO.Capture`, which saves the login on the host and gives the reply the VM gets, with placeholders and no refresh token, so the endpoint's reply never reaches the VM ([capturing logins](#capturing-logins));
- carries at most 1024 `CONNECT`s at once (`maxConnects`), links' and intercepted ones too, and answers `503` past it, logged as a refused block, and once in its own log until a tunnel ends;
- with `nix_cache`, answers `http://devvm.proxy/nix/` itself, as a Nix binary cache that VMs share and only the host fills (below);
- logs every decision as JSON lines, and keeps why a name didn't resolve or a tunnel didn't connect in its own log: the VM's `403`, `/blocked` and the event log get a reason that names neither the host's DNS server nor the company proxy (`reasonUnresolvable`, `reasonConnectFailed`).

For a VM whose image has the nix layer, devvm sets `nix_cache`, and the VM's Nix tries `http://devvm.proxy/nix` before `https://cache.nixos.org`. The proxy takes only `GET` and `HEAD` of `nix-cache-info`, `<32 nix-base32>.narinfo` and `nar/<52 nix-base32>.nar` (bare, `.xz`, `.zst` or `.bz2`), with no query, and answers `400` to anything else. It makes up `nix-cache-info` itself, at priority 30, and fetches the rest from `https://cache.nixos.org` alone, only when the VM's policy allows `cache.nixos.org:443` and, by its rules by method and path, a `GET` of the path asked for (`policy.judge`), through the floor or the company proxy, never following a redirect and sending nothing of the VM's request. Before keeping a narinfo, it checks its signature by the pinned `cache.nixos.org-1` key over its fingerprint (`1;StorePath;NarHash;NarSize;References`), that its StorePath is the one asked for, and that its URL is named by its own `NarHash` or `FileHash`. It fetches a NAR only after a narinfo it checked names it, never for a `HEAD`, each one once however many ask and at most four at once, and keeps it only when its SHA-256 and size are that narinfo's `FileHash` and `FileSize`. Files are written whole and renamed into the folder, mode 600 in folders of 700. Anything that fails answers `404`, and nothing of it is kept, so Nix goes to cache.nixos.org itself. Under a lock (`flock` on `.lock`), the proxy takes each file's room in whole blocks before it writes it (`reserve`), deleting the least recently used files (by modification time, which a hit updates) when the file would take the cache past `nix_cache_max`, down to nine tenths of it, and `.size` keeps the running total. A NAR being fetched is made its full size at once and counts against the cap, so a fetch that would pass it with them is refused. devvm gc and the retention settings trim it with `TrimNixCache`, under the same lock.

With `links`, the proxy is a second entrance to the VM's [links between VMs](../../docs/content/docs/internals/network.md#links-through-the-proxy), beside the ssh remote forward that carries every link. `devvm _links` writes every link the VM has, carried or not, to the list (`LinkList`, JSON, version 1) whenever they change, and leaves it when it ends, so a link with no socket is refused rather than asked of the rules, and the proxy checks it for every request and reads it again when it has changed (`watched`), a list it can't read having no links, logged once: a regular file, not a symbolic link, that only its owner may write, at most 1 MiB. After the password and before any rule, it lowercases the host, drops one trailing dot, and looks for an entry that names that host (`NAME` or `NAME.devvm.internal`) and port exactly. It takes an entry only when its socket is `LinkSocket` of the sockets' folder (`link_sockets`, devvm's run folder; without it, no link is reached), the VM (`vm`), the entry's address and its port, which is how `vmssh.Links` names it, and its address is in `127.77.0.0/16`, so the proxy never connects to another VM's link or to any other socket. Any other host under `devvm.internal` gets `403`, logged as a refused block, before the rules. A `CONNECT` is tunneled to the socket as it is, with no SNI check, no interception and no secret, and an absolute-form `http://` request goes there in origin form, without the proxy's headers, over a new connection for each request, which ends when the client gives it up. An `https://` request in absolute form gets `400`. The proxy logs nothing for a link it carried, because `devvm _links` logs it, and when the socket doesn't answer, after a few tries for a full backlog, it answers `502` and logs `link_refused` (`not carried`).

Once it listens, it says so with the address it listens on (`daemon.Ready`) in the status file that devvm names in its environment (`DEVVM_DAEMON_STATUS`), which is what devvm waits for as it starts the proxy. It returns when the VM's hostagent is gone.

## How devvm runs it

`internal/cli/proxy.go` is the hidden `devvm _proxy` command: it hands its arguments to `Main` with the run UI's streams (`IO`: the event log and `-help` on its `Stdout`, the proxy's own log lines on its `Stderr`), devvm's own files (`IO.FS`, which is `assets.FS`, so the package never imports `assets`), the lookup of secrets' values (`IO.Secret`, which is `secrets.Store.Get`) and the capture of logins (`IO.Capture`, which is `netpolicy.Capturer`), so the package never imports `internal/secrets` or `internal/agentlogin`, and returns an error as its failure, in `proxy_failed`. The package itself prints nothing.

```text
devvm _proxy -config ~/.local/share/devvm/vms/<hash>/run/proxy.json
```

Flags take one dash or two. The proxy has one, `-config`, and everything it runs with is in that file, `Config` as JSON, which `netpolicy.Proxy` writes for a VM's proxy and `backend.ProxyStarter` for a build's, each whole (`Encode`), mode 600, before it starts the proxy. The file holds the VM's password and the company proxy's credentials, which is why none of it is in the arguments: a process's arguments are visible to other users. `ReadConfig` reads it once, as the proxy starts: a regular file, not a symbolic link, owned by the proxy's user and readable and writable by nobody else, at most 1 MiB, of `ConfigVersion` (`"version": 1`), with no field `Config` lacks (`DisallowUnknownFields`), with a password, a loopback `listen` address, `ca` and `ca_key` together and a `nix_cache_max` of at least 0. Anything else is an error, and the proxy never listens. A running VM's proxy starts again when the config devvm would start it with has another `Sum`, the SHA-256 of its encoding.

| Field | What |
| --- | --- |
| `version` | `ConfigVersion`, 1: a file of another isn't read |
| `listen` | the VM's proxy port, on loopback; port 0 for any free one (a build's) |

| `password` | the VM's key: requests need it as the proxy password, user `devvm` |
| `builtin_policies` | devvm's built-in policies, paths in `IO.FS` (`layers/base.policy`, `shared-tools/node.policy`), in order: read once as the proxy starts, ahead of `policies`, and never again; one that's missing, or holds a line that isn't a rule, is devvm's bug, so `Main` returns an error and the proxy never listens |
| `policies` | the user's policy files, in order, each re-read when it changes; a missing file has no rules |
| `deny_policies` | policy files after `policies`, read as they are, whose denies alone apply: their allows are dropped as they're read, and a broken deny still refuses everything (the internet and none tiers' user files) |
| `open` | every host and address on every port, internal ones and this machine's included: no rule or floor applies, and a name the host can't resolve goes to `upstream` unjudged; refused together with any policy (an open VM's) |

| `ca_next`, `ca_next_key` | with `ca`: the VM's next CA, which signs from an hour after its start; the VM trusts it too |
| `secrets` | the VM's bindings file, `BindingList` (no values), re-read when it changes ([secrets](#secrets)); `Main` refuses it without `IO.Secret` |

| `upstream` | the host's `HTTPS_PROXY`, `HTTP_PROXY` and `NO_PROXY` (`https`, `http`, `no_proxy`): allowed requests go through that company proxy, which gets host names, and its credentials only in its own `Proxy-Authorization`; logs name it by `host:port` |

| `devvm_sha256`, `ca_sha256`, `ca_next_sha256` | the SHA-256 of the devvm binary, of the VM's CA certificate and of its next one's: not read by the proxy, there so a new binary or CA changes the config's `Sum` and devvm starts the proxy again |

Running the proxy is `Main`'s only mode. What only the host does for network policy runs in devvm itself, never through the proxy's arguments: `trust.InitCA` readies the VM's own CA and its next one in the VM's `run/ca/` (`ca.pem` and `ca.key`, `next.pem` and `next.key`, each written whole; each valid 30 days; no host name in them), and the proxy signs with the next one from an hour after its start, and `internal/agentlogin` makes the VM's copies of agents' login and settings files, their bindings and their values.

## The server

Everything a proxy runs with, and everything it keeps between connections, is in its `server`, which `newServer` makes from the config as the proxy starts. The package keeps no state of its own: its only package-level variables are error sentinels and fixed tables (`notPublic`, `withIPv4`, `githubMinting`), which the structure test allows. The server holds the VM's name and password, its own log, and these parts, each of which keeps what it changes under a lock of its own:

- `events`: the event log and the last 50 blocks, for `/blocked` and `/blocked/new`;
- `egress`: the policy (`policy`, which reads the user's files again when they change), the host's own addresses (`hostAddrs`, read again every 30 seconds) and the company proxy (`upstreams`, set as the proxy starts and only read after);
- `secrets`: the bindings file, read again when it changes, and the values looked up for it, held through each lookup so lookups go one at a time;
- `ca`: the VM's CA, its next one, and the certificates the proxy has made with each;
- `links`: the links' list and their sockets' folder, which are only read;
- `nixCache`: the Nix cache's folder, which every proxy shares under its `.lock`, and the narinfos this proxy has checked and the NARs it's fetching.

A test makes a server of its own with `newServer`, as `Main` does, and sets on it whatever else it needs, so no test changes another's proxy and the tests run in parallel.

## Secrets

The bindings file, `secrets.json` in the VM's run folder, is a `BindingList`: `{"version": 2, "bindings": [...]}`, which `secrets.Store` writes whole, mode 600, at each launch and again whenever a secret is saved, deleted, bound or unbound. Each `Binding` has its `name`, its `kind`, its `hosts`, its `header` and its `placeholder`, sometimes a `path` and `methods`, and never a value. Its kind says where the value comes from: `secret` is one that devvm keeps (`devvm secret set`), yours included, in the Keychain or in devvm's secrets folder, and `login` is one of an agent's logins, read from the login file of its `agent` (such as `codex`, `opencode`, `pi` or `claude`) on the host each time. The kind also says how the value goes in (`Binding.takes`), so the VM can't put the value where a server echoes it, or bytes of its own around it. A secret's placeholder is replaced only when exactly one value of its header holds it, and that value is the placeholder alone, or in `Authorization`, `Bearer`, `Token` or the binding's own `scheme` (never `Basic` or `Digest`: `SchemeOK`), one space and the placeholder, or `Basic` credentials whose password is the placeholder, or with `basic_user` whose username is (`secretValue`). A login's is replaced only when the header has one value that's the placeholder alone, or `Bearer`, one space and the placeholder in `Authorization`. A secret of yours' binding also carries its definition's `id`, which the lookup checks it against. A binding with a `path`, a pattern as a rule's is (`PathOK`), such as `/api/` for everything below `/api/`, or with `methods`, such as `GET,HEAD`, gets its value only for a request that they match, as it goes upstream, as a rule's allow matches it (`match.allows`): the path plain, clean, unencoded and without a backslash or `;`, and the method, and each method-override header, among the methods as written. Nothing about a binding is worked out from its name. The proxy reads the file with `ReadBindings` when its modification time changes: a regular file, not a symbolic link, owned by the proxy's user and readable and writable by nobody else, at most 1 MiB, of version 2, which a proxy that knows only version 1 refuses, so it puts no value in rather than put one in for every method, or of version 1 without methods or a `*` in a path, each binding of a kind it knows, and each `path` and `methods` one it takes. A file it can't read that way has no bindings until devvm writes it again, and the proxy logs why once. A change also drops every value it has cached.

The proxy looks a value up in its own process, through `IO.Secret`, which `devvm _proxy` sets to `secrets.Store.Get`, so no other devvm runs for it, and no value is in any process's arguments. On macOS the Keychain is still asked through `security find-generic-password`, whose output is the value, as when you save one. `Main` refuses a config with `secrets` and no `IO.Secret`. The lookup gets the binding itself, so the kind decides whether it's the Keychain, devvm's secrets folder or the agent's file (`agentlogin.File.Get`, which refreshes an OAuth login on the host when it's due, under the file's lock). Each lookup's context carries the route of the proxy's own company proxy, with its password (`WithRoute`), and a refresh goes through it (`RouteOf`), so it leaves the host the way the VM's requests do. The context also carries the proxy's own roots, the system's and `upstream_cas` (`WithRoots`), which a refresh trusts (`RootsOf`), so a company proxy that inspects TLS doesn't refuse it. A proxy without `upstream` gives a direct route. It runs for at most 20 seconds and one at a time, so two requests never refresh a login at once. The proxy keeps a value for 5 minutes, or for 30 seconds when its kind is `login`, by its binding's kind, agent and name together (`valueKey`), so a secret of yours and an agent's login never get each other's value, and it never logs it, and a lookup that fails or gives nothing puts nothing in and is logged, without a value, to the proxy's own log.

## Capturing logins

`captures` lists the token endpoints of the VM's agents, each an agent, a host and a path, such as Codex's and opencode's `auth.openai.com` and `/oauth/token`. The proxy intercepts a host that has one on `:443` as it does a host with a bound secret, with or without bindings, and forwards each request to it as it does any other. A `POST` whose path is an endpoint's, once it's cleaned (`path.Clean`), without its path parameters (`;x`) and in any case, is captured, for every agent whose endpoint it is, and goes to the endpoint's own path, without a query (`capturing.path`). The proxy reads its body whole, at most `captureRequestMax` (64 KiB), and hands it to `IO.Capture`'s `Request` in an `Exchange`, with the VM, the agents, its `User-Agent` and its `Content-Type`. The body `Request` returns is what goes out, or the answer it returns is the VM's reply, and the request goes nowhere. At most `captureReads` (8) requests and replies to and from the host are read whole at once. No `1xx` from the host reaches the VM (`no1xx`), and an upgrade (`101`) is refused. Every request to the host goes without the VM's `Accept-Encoding`, so Go's transport asks for gzip itself and undoes it. `ModifyResponse` (`captureResponse`) takes a successful reply (`2xx`) whole, at most `captureReplyMax` (1 MiB), and hands it to `Response`, which saves the login on the host and returns the reply the VM gets and whose login it was. The proxy sends the VM that reply alone, with its own `Content-Length` and only the headers that can't hold a credential (`keepHeaders`: `Content-Type`, `Cache-Control`, `Pragma` and `Date`), and logs a `login` event, which names the agent. An error reply reaches the VM as it is, unless `Request` changed the request's body, putting a real value in, when the VM gets only its OAuth error code (`errorReply`), in case the message quotes the request. Any other successful reply from the host, to a request that wasn't captured, is refused when it names an `access_token`, a `refresh_token` or an `id_token` anywhere, whatever its type (`guard`), so another path there can't hand the VM a login; a web page and its parts pass unread (`page`), and one guard can't read is refused. When `Response` returns a reply and an error, the login was saved, so the VM gets the reply and the error goes to the proxy's own log. A request or a reply that's too long, a reply with a `Content-Encoding`, or one that `Request` or `Response` refuses gets `502`, logged as a refused block, and why goes to the proxy's own log, which never holds a value from either: `Capturer`'s errors name none. Each call gets the lookup's 20 seconds, and the request's end doesn't cancel it, because the endpoint may already have replaced the refresh token.

`agentlogin.Endpoints` lists Codex's and opencode's endpoint and Claude Code's two, `platform.claude.com` and `console.anthropic.com` with `/v1/oauth/token`, for every VM, whatever its image holds. `netpolicy.Capturer` is `devvm _proxy`'s `IO.Capture`: it reads the VM's state for its salt, picks the agent, the image's when it has one of the endpoint's, else by `User-Agent` (`agentlogin.Pick`), and has `secrets.Store`'s `CaptureRequest` and `Capture` read and write the store's login file through `agentlogin.File`, or for `claude setup-token`'s token the `claude` secret, then writes the VM's bindings again, which the proxy reads at its next request.

Inside the VM, `http://devvm.proxy/blocked` lists recent blocks, `/blocked/new` those since the last prompt, `/ca.pem` serves the VM's CA certificate and the next one's, and with `nix_cache`, `/nix/` is the shared Nix cache.

## Testing

`go test ./internal/proxy` runs the unit tests, in parallel, each with a server of its own ([the server](#the-server)), and the fuzz targets' seeds; `go test -fuzz FuzzRequest ./internal/proxy` fuzzes one. `testdata/script/proxy.txtar` runs `devvm _proxy` itself and checks that it refuses any flag but `-config`. `nix_cache.txtar` runs it with a config of its own. `internal/agentlogin` and `internal/trust` have the tests of the logins, the redaction and the CA, and `internal/secrets` those of `Store.Get`, the lookup `IO.Secret` runs; the proxy's own tests give it a fake one. `internal/agentlogin` has the tests of each agent's capture, and `internal/netpolicy` those of `Capturer`; the proxy's own give it a fake `IO.Capture` and a fake token endpoint (`capture_test.go`).
