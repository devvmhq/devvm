# Changelog

What's changed on `main` since the latest release is in [Unreleased](#unreleased), at the bottom of this page.

## 0.2.0-rc.1

This is a release candidate for 0.2.0, and it adds to 0.1.1-rc.3. 0.2.0 takes 0.1.1's place, because its breaking changes need a new minor version. Install it with `devvm upgrade --to 0.2.0-rc.1`, the install script's `--version 0.2.0-rc.1`, or `brew install devvmhq/tap/devvm-rc`. Homebrew's `devvm` stays on 0.1.0.

### Breaking

- **At most 17 VMs run at once:** each VM's ssh now uses one of the 17 ports from 1024 up that every browser refuses, and a start past 17 fails and names the VMs that run on those ports, so stop one of them first. Root in a VM could make its ssh port answer as a web server and get the cookies of the apps you use on `localhost`, even in a VM that forwards no ports, and now no page in your browser reaches a server in a VM through that port ([too many VMs at once](https://next.devvm.dev/docs/using/troubleshooting/#too-many-vms-at-once)).
- **A VM that forwards every port leaves out those 17 ports:** a server in the VM on one of them, such as an X server on 6000, reaches this machine only when you list its port with `devvm ports`. That way a VM can't take the ports that other VMs' ssh needs, and `devvm ports` and each launch warn when a VM's list names one of them ([ports](https://next.devvm.dev/docs/using/ports-size/#ports)).
- **A short host name no longer reaches a host through the proxy:** a tool in a VM that reached a host on your company's network by a name such as `jenkins` now needs the host's full name, such as `jenkins.corp.example.com`, because the proxy no longer adds this machine's DNS search domain ([a name that doesn't resolve](https://next.devvm.dev/docs/using/troubleshooting/#a-name-that-doesnt-resolve)).
- **The agent store keeps only what a seed has of Claude Code's plugins:** if you imported Claude Code's settings with devvm 0.1.0, which copied your whole `~/.claude/plugins`, the first start of any VM takes your plugins' data out of devvm's agent store, where every VM with Claude Code could read it, along with the folder's other entries that are this machine's own, such as `installed_plugins.json`. It warns once, naming what it took, and it leaves your own `~/.claude/plugins` as it is. If the store's plugins folder is a link, or below one, which only a store you made yourself can be, no VM with Claude Code starts until you make it a folder of its own, because a VM's mount would follow the link ([Claude Code's plugins](https://next.devvm.dev/docs/using/coding-agents/#claude-codes-plugins)).
- **`devvm agent import` and `devvm agent save` refuse a linked store:** they now fail before they change anything, naming the link, when a folder on the way to what they write in devvm's agent store is a link, from `~/.config/devvm/agents` down, such as `~/.config/devvm/agents/claude` linked into a dotfiles repo. Make that folder one of its own, then run the command again. They used to write through the link and take out whatever they hadn't written in the folder it led to, which for a link to your home folder deleted your files ([devvm's agent store](https://next.devvm.dev/docs/using/coding-agents/#devvms-agent-store)).

### After you upgrade

- Run `devvm update` in each existing VM's folder. The new mise and Docker change what goes into the images, so until you do, a VM made from an older image says it's outdated, and every existing VM says there are newer shared tools at the same versions. The first update or new VM builds base and each of its shared tools again, one at a time, which takes several minutes.
- Each existing VM's ssh moves to one of the 17 ports that browsers refuse at the VM's next start. That's the one change devvm makes to the VM's Lima config, and like any change there, it gives the VM new ssh host keys. A VM that runs as you upgrade keeps its old port until then, and devvm warns of it at each launch, so run `devvm stop` in its folder, and its next start moves it ([too many VMs at once](https://next.devvm.dev/docs/using/troubleshooting/#too-many-vms-at-once)).
- A VM's proxy that runs as you upgrade stays one process, without a sandbox, until the VM's next launch. That launch starts it again as two processes, because a launch starts a VM's proxy again for every new devvm, and until then, `devvm doctor` names each VM whose proxy an older devvm started ([the proxy runs without a sandbox](https://next.devvm.dev/docs/using/troubleshooting/#the-proxy-runs-without-a-sandbox)).
- A VM that forwards an SSH agent and runs as you upgrade keeps the agent as it was until its next start, so it can still remove, lock or add keys, and devvm warns of it each time it opens the VM or changes its links. Run `devvm restart` in its folder to give it the relay at once ([agent forwarding](https://next.devvm.dev/docs/using/ssh/#agent-forwarding)).
- If you imported Claude Code's plugins with devvm 0.1.0 and a plugin's data held a login of the plugin's own, every VM with Claude Code could read that login, so sign in to that plugin again where you don't trust those VMs.
- A VM that runs as you upgrade, with Claude Code's plugins imported by devvm 0.1.0, loses the store's entries that are this machine's own from its mount at the first start of any VM, so Claude Code there may not find the store's plugins until that VM's next launch. On a Linux host, the VM can keep seeing what it had read of them until its next start.
- Each VM gets its own `~/.claude/plugins` at its next launch, without a restart, in place of its link to the store's folder. Claude Code started in a shell that was open before that launch finds none of the store's plugins, so start it in a new shell ([Claude Code's plugins](https://next.devvm.dev/docs/using/coding-agents/#claude-codes-plugins)).
- If a VM's copy of an agent's settings file had `devvm-redacted` under a name you chose, such as a plugin's marketplace, the VM's next launch writes the whole copy over the VM's own. Until then, `devvm agent save` leaves that file out and warns, so make any change to it in devvm's agent store, or launch the VM again and make the change there.
- Each VM records its project folder's volume at its first launch that finds the folder. Until then, a folder that moves while a restart gives its disk another device number still needs `devvm adopt VM`, and after a restart, the VM's gone folder can still be called not connected. Both stay true for a VM whose folder was already gone before the upgrade, because it never records a volume ([a moved or renamed folder](https://next.devvm.dev/docs/using/vms/#a-moved-or-renamed-folder)).

### Changed

- **Each VM's proxy runs as two processes:** only `devvm _proxy` reads your Keychain, your agents' login files and your other files, and `devvm _proxy-child`, which reads the VM's network, asks `devvm _proxy` for the rest, such as each connection and each value bound to the VM. So besides the VM's own proxy password and CAs and your company proxy's password, the code that reads every byte a VM sends holds only the values that the VM's own bindings name, each for a few minutes after it was last asked for, and never a new login's tokens, its refresh token among them. An error reply from an agent's token endpoint reaches the VM as it is up to 1 MiB, and gets `502` past that, and a build's proxy writes its logs to a `logs/` folder of their own in its folder ([a VM's proxy](https://next.devvm.dev/docs/internals/processes/#a-vms-proxy)).
- **On macOS, the proxy's child runs in a macOS sandbox:** `devvm _proxy-child` starts under `sandbox-exec`, with a profile that lets it write only its VM's logs and the shared Nix cache and look at your policy files. A bug that a VM drove there couldn't read your files, reach the Keychain or connect to this machine's unix sockets, such as ssh's and Docker's ([the proxy runs without a sandbox](https://next.devvm.dev/docs/using/troubleshooting/#the-proxy-runs-without-a-sandbox)).
- **On Linux, the proxy's child confines itself:** before it reads a byte of the VM's, `devvm _proxy-child` confines itself with Landlock and a seccomp filter. A bug that a VM drove there could read and write only its VM's logs and the shared Nix cache, and couldn't change any other file's mode, owner, attributes or times, run a program, or connect to a unix socket, such as an ssh master's, Docker's or your SSH agent's. It could still learn whether a file of yours exists, its size and when it changed ([the proxy runs without a sandbox](https://next.devvm.dev/docs/using/troubleshooting/#the-proxy-runs-without-a-sandbox)).
- **A proxy that can't get its whole sandbox keeps the VM's network, and `devvm doctor` warns:** on macOS, if `sandbox-exec` is missing or fails to start the child, the child runs without the sandbox. On Linux, a kernel without Landlock or seccomp filters, or whose Landlock is older than ABI 6 or lacks its fix for signals between threads, confines the child only in part. Either way the VM keeps its network, and `devvm doctor` warns for each VM whose proxy runs that way, naming what the kernel lacks on Linux ([the proxy runs without a sandbox](https://next.devvm.dev/docs/using/troubleshooting/#the-proxy-runs-without-a-sandbox)).
- **The proxy's child connects only through `devvm _proxy`:** wherever its sandbox runs, a bug that a VM drove in the child can't reach this machine's services on `localhost`, such as your dev servers, Docker's published ports and other VMs' proxies, nor this machine's own addresses or your LAN's private addresses, unless a rule names the address, just as the VM can't. A rule such as `devvm network allow 127.0.0.1:5432` still applies from the next connection, and a company proxy on `localhost` still works, though the child reaches whatever that company proxy reaches, as the VM does. Because `devvm _proxy` looks up the child's names, the child reads no file below `/etc` on Linux and doesn't talk to mDNSResponder on macOS ([the child's sandbox](https://next.devvm.dev/docs/internals/network/#the-childs-sandbox)).
- **`devvm doctor` checks every VM's state:** it warns once of each VM whose state devvm can't read, naming the VM, the file and why, even when it can't read the VM's folder, and it changes nothing. It reads each VM's `vm.json` as every command on a VM does, and such a VM no longer hides doctor's warnings about the other VMs' policy files, nor the warnings that `devvm network` gives for every VM ([a file devvm can't read](https://next.devvm.dev/docs/using/troubleshooting/#a-file-devvm-cant-read)).
- **A marketplace's credential gets a warning:** `devvm agent import` and `devvm agent save` now warn when they copy a Claude Code marketplace that has a password or an access token in its clone's git config or in its source in `known_marketplaces.json`, because every VM with Claude Code can read it. The warning names the marketplace, the store's file and the keys, and the marketplace is copied as before ([mounts](https://next.devvm.dev/docs/using/coding-agents/#mounts)).
- **`devvm agent import` has bounds:** it copies at most 20,000 files, folders and links, 128 MiB, and 16 MiB in one file, of each agent's folder. An agent's folder that holds more, such as one that a VM's project inside it filled, fails the import before the store changes, naming the folder, so take out what it doesn't need and import again ([importing from this machine](https://next.devvm.dev/docs/using/coding-agents/#importing-from-this-machine)).
- **A failed `devvm agent import` leaves the store as it was:** that holds whether the import fails while it reads, such as at a file that changed meanwhile, or while it puts the settings and logins in place, such as at a login it can't save. In the rare case that putting the store back fails too, the import names what it kept ([importing from this machine](https://next.devvm.dev/docs/using/coding-agents/#importing-from-this-machine)).
- **A project in an agent's folder gets a warning:** when a VM's project folder is inside a coding agent's folder on this machine, such as a skill you work on in `~/.claude/skills/mine`, or holds one, such as `~/.pi`, code in the VM can change that agent's settings on this machine, and so the settings that `devvm agent import` copies for every VM. Each launch of the VM now warns of it in one line, and so does the import, which also leaves out an agent's folder that a link in a VM's project folder leads elsewhere ([project folders devvm refuses](https://next.devvm.dev/docs/using/settings/#project-folders-devvm-refuses)).
- **`devvm agent import` follows no links while a VM's state can't be read:** it warns of each VM whose state it can't read, because it can't tell where that VM's project folder is. Until that's fixed, it leaves out every link out of an agent's folder, and an agent's folder or login whose path leads through a link, one on the way to your home folder included unless only root can change it, naming the state, so run `devvm doctor` and import again ([importing from this machine](https://next.devvm.dev/docs/using/coding-agents/#importing-from-this-machine)).
- **Cursor's CLI in a VM can change less of your Cursor account:** its proxy refuses more of the methods that change your account, your team or your cloud agents, such as merging a cloud agent's pull request, forking or pinning a cloud agent, or writing to its machine, and every call that the CLI itself makes still passes. Do those from Cursor on your machine ([Cursor CLI login](https://next.devvm.dev/docs/using/coding-agents/#cursor-cli-login)).
- **Pins:** mise is 2026.11.10, in base and on this machine, the docker layer's Docker is 29.10.0 and its compose 5.8.0, and Cursor's CLI is 2026.11.17-f532c45. The new mise and Docker change what goes into the images, so base, every image built on it and every shared tool that mise installs are built again once.
- **Slow steps show a status line:** in a terminal, devvm now shows what it's waiting for during these steps ([a command fails](https://next.devvm.dev/docs/using/troubleshooting/#a-command-fails)):
  - finding the folder's VM, checking it before a start, checking its network and reading its host keys, setting it up, running a `devcontainer.json`'s commands, looking up a folder's disk, checking Lima, deleting a VM or an image, applying the retention settings and installing an upgrade
  - `devvm ls` reading the VMs, `devvm doctor` checking this machine, `devvm agent import` reading your agents' folders and copying them into the store, and `devvm agent save` reading and comparing the VM's settings
  - `devvm clone add`, `clone fetch`, `clone on` and `clone off`, `devvm git-protect`, `devvm stop`, a `--clone` VM's check before `devvm rm`, a history export or import, and `devvm ports` as it starts a running VM's port forwarder again
  - `devvm link` as it asks about the VMs its links lead to, `link add`, `link rm`, `link publish` and `link unpublish`, `devvm group join` and `group leave`, and `devvm rm` of a VM that others link to, as they give each running VM its changed links and check the VMs that links lead to
  - `devvm network learn` and `network lock` as they give a running VM's proxy its new tier
  - every stop of a VM, as for `devvm restart` or a restart you agree to after changing a setting
- **Waiting for another devvm shows a status line:** while devvm waits for another devvm that's changing the same thing, such as a VM's state, its folders' layout, a group, an image's build or the shared tools, a status line says so, and only while it waits. Some of those waits used to show nothing, and others printed a line after a few seconds that stayed, which a run with `-v`, or with its output piped, no longer prints, because a status line shows only in a terminal without `-v` ([a command fails](https://next.devvm.dev/docs/using/troubleshooting/#a-command-fails)).

### Fixed

- **devvm says when it can't read a project folder:** when you, or code in a VM that mounts it, take away your read permission on a project folder, devvm now names the folder and why it can't be read, so make it readable again. It used to say that the folder's VM was made for an earlier folder that was deleted or replaced, and offer `devvm rm` and `devvm adopt` ([a folder made again](https://next.devvm.dev/docs/using/vms/#a-folder-made-again)).
- **A warning no longer lands on the status line:** a message that devvm prints during a slow step now prints above the status line, which comes back below it, and a question, the picker and an agent's login in the VM take the status line away until they're done. A warning used to be written onto the status line's own line, and the status line's next redraw could erase a question's prompt and what you typed ([a command fails](https://next.devvm.dev/docs/using/troubleshooting/#a-command-fails)).
- **`devvm agent login claude --setup-token` shows Claude Code's address (#57):** when devvm runs in a terminal, an agent's login in the VM now gets a terminal of its own, as devvm's shell does, so Claude Code shows the address to open and the prompt for its code. The login used to get none, so `claude setup-token`, which draws full-screen, showed nothing and waited. Without a terminal, `--setup-token` warns that the login may show nothing ([Claude Code login](https://next.devvm.dev/docs/using/coding-agents/#claude-code-login)).
- **Ctrl-C ends an agent's login in the VM:** in a terminal, Ctrl-C now goes to the agent's login in the VM and ends it, and devvm then says that the login ended or saved nothing. devvm puts the terminal back as it was before the login, even when a signal ends devvm itself ([Claude Code login](https://next.devvm.dev/docs/using/coding-agents/#claude-code-login)).
- **The VM's shell gets your terminal's 24-bit color (#54):** devvm's shell in a VM and an agent's login with `devvm agent login` now get your terminal's `COLORTERM` when it's `truecolor` or `24bit`, and no other value, so programs in the VM, such as coding agents, no longer fall back to fewer colors ([opening a VM](https://next.devvm.dev/docs/using/vms/#opening-a-vm)). They never got it before, and neither did `ssh` to a VM by name, whose ssh config entries now send it as your terminal has it, from the next time devvm launches or stops a VM, which writes them again. A VM made with `--from` gets it over ssh only when its image's sshd accepts it ([ssh access by name](https://next.devvm.dev/docs/using/ssh/#ssh-access-by-name)).
- **MCP servers' logins in a VM finish and stay (#62):** with your subscription's login, devvm now replaces only the Claude login in the VM's `~/.claude/.credentials.json`, where Claude Code also keeps its logins to MCP servers, and keeps the rest. So the MCP servers' logins you make in a VM stay in that VM, and they never reach this machine or another VM. Each launch and each `devvm agent login claude` used to write devvm's copy of the login over the whole file, so a login to an MCP server that you started with `/mcp` in a VM failed when devvm set the VM up again before it finished, such as when you ran devvm in its folder from another terminal, and one that finished was gone at the VM's next launch. With a Claude Code token, the VM's file stays as it is ([MCP servers' logins](https://next.devvm.dev/docs/using/coding-agents/#mcp-servers-logins)).
- **Your claude.ai connectors work in a VM (#61):** with your subscription's login, the VM's proxy now also puts the login into requests to `mcp-proxy.anthropic.com` below `/v1/mcp/`, which carry the connectors' traffic, from each VM's next launch. So a VM with Claude Code can use every connector you added in claude.ai, as Claude Code on this machine can. The proxy used to put the login only into requests to `api.anthropic.com`, so the connectors' requests held the login's placeholder and were refused. Code in the VM can now read and act through your connectors, so disconnect the ones you don't want VMs to use, or deny `mcp-proxy.anthropic.com` with `devvm network deny` ([your claude.ai connectors](https://next.devvm.dev/docs/safety/attack-vectors/#the-network)). A Claude Code token, from `claude setup-token` or in devvm's environment, still goes only to `api.anthropic.com` ([Claude Code login](https://next.devvm.dev/docs/using/coding-agents/#claude-code-login)).
- **A `NO_PROXY` address with a zone no longer goes direct (#59):** an IPv6 address with a zone in your company proxy's `NO_PROXY`, such as `fe80::1%eth0`, now matches nothing, as it does in Go's HTTP clients. Such an entry used to send that address past the company proxy without its zone ([behind a company proxy](https://next.devvm.dev/docs/safety/network/#behind-a-company-proxy)).
- **Claude Code's plugins work in a VM (#56):** each VM's `~/.claude/plugins` is now its own folder, so what Claude Code writes there works, such as a plugin's data in `${CLAUDE_PLUGIN_DATA}`, installing a plugin and updating a marketplace. It used to be devvm's agent store's folder, mounted read-only, so all of those failed. The store's plugins are now Claude Code's read-only seed at `~/.claude/plugins-seed`, so they load as before, a plugin keeps its data in the VM, and a plugin you install in a VM stays in that VM until `devvm agent save` copies it into the store. A store that devvm 0.1.0's import filled keeps only what a seed has, as Breaking above says ([Claude Code's plugins](https://next.devvm.dev/docs/using/coding-agents/#claude-codes-plugins)).
- **devvm's own folders are refused in any case on a Mac:** devvm now compares a project folder with your home folder and its own folders by the folders themselves as well as by name, so on a Mac, where a name's case doesn't count, it refuses a project at `~/.Config/devvm/layers` as it refuses `~/.config/devvm/layers`. Such a project used to get a VM with read-write access to devvm's settings and layer scripts. A VM already made in such a folder still mounts it, so delete it with `devvm rm` there. devvm also refuses an SSH key in a folder that a VM mounts by a name in another case ([project folders devvm refuses](https://next.devvm.dev/docs/using/settings/#project-folders-devvm-refuses)).
- **A project folder's VM works after your Mac restarts (#60):** a folder at the same path, with no link on it and with the same inode and birth time, is now the same folder on whichever device it's on. After a restart, an unchanged folder could be on a device with another number, and devvm took it for another folder. So every command on its VM refused it as made for an earlier folder at its path, a stopped VM's start refused it as replaced, and the next check of `.git` called it replaced. The VM's next start records the folder on its new device before it mounts it, in the one change devvm makes to its Lima config. A folder that moved after a restart, before its VM started again, isn't offered the VM, so `devvm adopt VM` moves it ([one VM per folder](https://next.devvm.dev/docs/internals/security/#one-vm-per-folder)).
- **A folder that moved across a restart keeps its VM:** each VM now records its folder's volume, which no renumbering changes, so devvm finds a folder that moved while a restart gave its disk another device number. It used to miss such a folder and make it a second VM, and it called the gone folder of a VM whose disk was renumbered not connected. Once the VM has recorded its volume, as After you upgrade says, devvm offers a moved folder its VM by its volume, inode and birth time, and calls a VM's gone folder gone ([a moved or renamed folder](https://next.devvm.dev/docs/using/vms/#a-moved-or-renamed-folder)).
- **A folder on another volume needs `devvm adopt`:** a folder at the VM's own path whose disk was renumbered, but on another volume than the one recorded, such as a copy of the disk with a volume ID of its own mounted there, is another folder, so devvm gives it the VM only after `devvm adopt`. On Linux, every launch checks the volume, so a Btrfs snapshot rolled back at the folder's path, or the folder after you give its volume a new UUID, also needs `devvm adopt` ([a folder made again](https://next.devvm.dev/docs/using/vms/#a-folder-made-again)). When devvm can't read the volume at the launch after a renumbering, such as when `diskutil` doesn't answer, each launch looks it up until it can ([one VM per folder](https://next.devvm.dev/docs/internals/security/#one-vm-per-folder)).
- **Two devvms no longer write the agent store at once:** `devvm agent import`, `devvm agent save` and a start that cleans Claude Code's plugins out of the store now take turns, so a second one says it's waiting and goes on once the first is done. Their files used to mix, or one could fail partway. A save that finds the store changed since it showed what differs now saves nothing instead of writing over an import ([importing from this machine](https://next.devvm.dev/docs/using/coding-agents/#importing-from-this-machine)).
- **A failed `devvm agent save` leaves the store as it was:** a save now saves all or nothing, as an import does, and in the rare case that putting the store back fails too, it names what it kept. A save that failed partway, such as at a file it couldn't write in one agent's store or at the Claude Code login it saves last, used to leave the agents it had saved before the failure saved and the rest not. A file in the VM where the store has a folder, or the other way round, now fails the save before anything changes, naming the store's path ([saving a VM's settings](https://next.devvm.dev/docs/using/coding-agents/#saving-a-vms-settings)).
- **`devvm agent save` and a VM's new Claude Code login take turns:** while it saves Claude Code's part of `~/.claude.json`, the save holds the lock on Claude Code's logins, the lock that a VM's proxy holds while it saves a Claude Code login made in that VM. Ctrl-C while the save waits for either lock ends the wait ([saving a VM's settings](https://next.devvm.dev/docs/using/coding-agents/#saving-a-vms-settings)).
- **`devvm agent save` has an import's bounds on depth:** a VM that sends folders nested more than 128 deep, or a path of more than 4,096 bytes, now gets nothing saved, as an import of such folders does. A chain of thousands of folders used to keep the save busy for a long time while it held the agent store's lock ([saving a VM's settings](https://next.devvm.dev/docs/using/coding-agents/#saving-a-vms-settings)).
- **Names that differ only in case no longer lose a file on a Mac:** `devvm agent save` and `devvm agent import` now treat a file whose name differs from the store's only in case, such as `foo.md` where the store has `Foo.md`, as one file, as macOS's volume does. So the store's file gets the new content and keeps its name, and the save's diff shows it as changed. When the VM, or your home folder for `devvm agent import`, had such a file, they used to delete the store's file and report success. Two names in the VM that differ only in case, such as `A.md` and `a.md`, would be one file in the store, so the save now saves nothing and names both, and so does an import of two such names from a home folder on a volume that tells case apart ([saving a VM's settings](https://next.devvm.dev/docs/using/coding-agents/#saving-a-vms-settings)).
- **A link inside an agent's folder copies only a setting:** `devvm agent import` now copies a link inside an agent's folder only when it leads to one of the settings the import copies, and leaves any other out with a warning that names where it leads. It used to copy such a link as the file it led to, wherever that file was in the folder, so a link in `~/.claude/skills` or `~/.claude/plugins/cache` could put your history, `~/.claude/.credentials.json` or a plugin's data into the store, where every VM with the agent reads it ([importing from this machine](https://next.devvm.dev/docs/using/coding-agents/#importing-from-this-machine)).
- **`devvm agent import` no longer copies your plugins' data into every VM:** from `~/.claude/plugins`, it now copies only the marketplaces, their records and the plugins' cache, and `devvm agent save` copies only those from a VM. The import used to copy all of the folder into the store, so every VM with Claude Code got the data that your plugins keep on this machine, which can hold their own logins ([importing from this machine](https://next.devvm.dev/docs/using/coding-agents/#importing-from-this-machine)).
- **An export can't put what an import leaves out into a VM:** `devvm history import` now refuses a name with a `.` or empty part, and once the export is unpacked, it deletes what it leaves out by its path. It used to leave out the agents' logins and the files that devvm's setup writes by their names as the export wrote them, so an export that spelled one another way, such as `.claude/./settings.json` or `.claude//plugins`, got it into the VM's home ([importing history](https://next.devvm.dev/docs/internals/agents/#importing-history)).
- **Names you choose in an agent's settings are no longer taken for secrets (#55):** devvm now knows the agents' tables of names, such as Claude Code's `mcpServers`, and judges only the fields under a name, so a server named `secret-scanner` keeps its command and still loses its `env` and its `apiKey`. It used to take a plugin, a marketplace or an MCP server whose name had `key`, `token`, `secret` or `passw` in it, such as `tokeneconomizer` or `secret-scanner`, for a secret, and put `devvm-redacted` in place of all its settings in the VM's copy, so Claude Code refused the VM's `settings.json` whole and every plugin was off in the VM. Thanks to @jspiro for the report and @dhruv1220 for the tests' idea in #58 ([keys in settings files](https://next.devvm.dev/docs/internals/network/#keys-in-settings-files)).
- **A folder whose name has separators in a row gets a VM (#52):** devvm now turns each run of characters other than letters and digits into one dash, so a folder named `x--y`, `foo (copy)` or `C++ stuff` gets a VM, and `foo (copy)` gets `devvm-foo-copy-<hash>`. It used to turn each such character into its own dash, and Lima refuses a name with dashes in a row. The state that such a folder's failed VM left is replaced when you run devvm there again. Thanks to @se6a for the report ([VM names](https://next.devvm.dev/docs/internals/backends/#vm-names)).
- **Lima's console logs no longer keep a VM's proxy password:** once the VM has started, devvm now replaces each password with as many `*` in Lima's console log for the VM, `serial.log`, `serialp.log` or `serialv.log` in the VM's folder in devvm's Lima home, as it does in `ha.stderr.log`. Lima's boot scripts write the VM's proxy settings, with the VM's own proxy password, to the VM's serial console, which Lima keeps in those logs, and devvm used to take the passwords out of Lima's `ha.stderr.log` only ([the run log](https://next.devvm.dev/docs/internals/overview/#the-run-log)).
- **A short name no longer reaches a denied host under your search domain:** the proxy now looks each name up as it's written, so with `api.corp.example.com` denied and `**` allowing the rest, a VM can no longer reach that host as `api`, or `api.eu.corp.example.com` as `api.eu`. The proxy used to look names up with this machine's DNS search domain, which macOS takes from the network's settings and Linux from `/etc/resolv.conf`, so when either host had a public address, no rule judged the name that the search domain made. A tool in the VM now reaches a host on your network by its full name, as Breaking above says, and a block for a name without a dot says to use its full name ([a name that doesn't resolve](https://next.devvm.dev/docs/using/troubleshooting/#a-name-that-doesnt-resolve)).
- **A VM can no longer take an SSH agent away from you or other VMs:** a VM now reaches its agent only through its proxy, which passes on listing keys, signing and binding a session to a host, and refuses everything else, so `ssh-add` in a VM can still list and use the keys, but not remove, lock or add them. A VM that forwarded your agent or devvm's own used to be able to remove every key from it with `ssh-add -D`, lock it with a password of its own with `ssh-add -x`, or add keys to it, and every VM that shares devvm's agent lost it then, and with your own agent, so did you. An editor's connection gets the same agent as devvm's shell, the one the VM started with. A VM that's running when you upgrade keeps the old behaviour until its next start, as After you upgrade says ([the SSH agents](https://next.devvm.dev/docs/internals/processes/#the-ssh-agents)).
- **A VM's host keys are pinned whatever its ports:** devvm now pins a VM's ssh host keys each time it starts the VM, whatever the VM forwards, and a command that finds the VM running without them pins them first. When other programs on this machine, such as your own dev servers, held every port a VM lists, or the VM forwarded none with `devvm ports none`, a start that went no further than starting the VM, such as `devvm clone fetch` on a stopped `--clone` VM, used to leave the keys unpinned. devvm's own ssh to the VM then failed until something else pinned them, so `devvm clone fetch` and `devvm rm`'s fetch failed with `clone_fetch_failed` ([ssh into VMs](https://next.devvm.dev/docs/internals/security/#ssh-into-vms)).
- **A removed link's connections end with it:** removing a link with `devvm link rm` now ends its open connections within a few seconds, and when a target starts again, the connections still open through its earlier start end as well. It used to stop only the link's new connections, so a target that never closed its end kept each open connection's ssh process on this machine, and one of the 256 connections a client's links carry at once, until the client or the target stopped ([removing a link](https://next.devvm.dev/docs/using/links/#removing-a-link)).
- **An agent's settings file that's one string no longer crashes `devvm agent save`:** when an agent's settings file in the VM is a single JSON string holding a placeholder, `devvm agent save` now puts the saved value back in it, where it used to crash. A login file on this machine that holds only `null` is now refused as not a JSON object, where saving a Codex or opencode login made in a VM failed on it ([saving a VM's settings](https://next.devvm.dev/docs/using/coding-agents/#saving-a-vms-settings)).
- **A closed connection's ssh process ends:** the ssh process of a forwarded port's or a link's connection now ends once its client has closed and the VM has sent nothing for 30 seconds. When a VM never closed its end, that process used to stay on this machine after the program here, or in the client, had closed its side, so a hostile VM could take all 256 connections that a forwarder or a client's links carry at once. So a program that stops sending and waits more than 30 seconds for an answer to begin, such as `nc -N` in front of a slow query, has its connection cut ([how it reaches the VM](https://next.devvm.dev/docs/internals/ports/#how-it-reaches-the-vm)).
- **A forwarded port answers on `::1` as well as `127.0.0.1`:** when this machine briefly can't listen on a port's IPv6 address, such as when it runs out of open files, the forwarder now tries the port again at the VM's next report and forwards it on both addresses. It used to forward the port on `127.0.0.1` alone until the server in the VM restarted, so a client that connects only over IPv6, such as `http://[::1]:PORT` or a tool that doesn't fall back to `127.0.0.1`, didn't reach the VM, and another program on this machine could take `::1` on that port and get those connections instead ([when it can't forward](https://next.devvm.dev/docs/internals/ports/#when-it-cant-forward)).
- **Every host is read as the proxy reads it:** a few of devvm's checks used to read a host in a way of their own. `devvm secret set --host`, an MCP server's URL and a `NO_PROXY` entry took a name with a letter that isn't plain ASCII, such as the Kelvin sign, which Unicode's case folding turns into `k`, as the ASCII name it folds into. `--from` took a registry's host with such a letter, or an address in brackets before a trailing dot such as `[::1].`, as one on the internet. The proxy now answers `400` to a host with brackets around anything but an IPv6 address, such as `[evil.com]:443`, and a partial clone's warnings now read a remote's host without its trailing dot, so they name `example.com`, not `example.com.`, and a remote at `localhost.` gets the same warning as one at `localhost`. The proxy refuses a host with such a letter, so now:
  - `devvm secret set` refuses it
  - an MCP server with one gets no secret
  - a `NO_PROXY` entry with one matches no host
  - `--from` doesn't take such a registry as public
  - `devvm network rm` with it never removes the rule with the plain letter ([how the proxy reads a host](https://next.devvm.dev/docs/internals/network/#the-proxy))
- **A VM can't fill a Linux host with processes:** on a Linux host, devvm now carries at most 256 of a VM's connections to its proxy at once, and answers any past that with `503` before it reaches the proxy. Each connection that a VM confined to its proxy makes to the proxy starts a devvm process on this machine, and with no limit, a VM that opened connections without end could start thousands of them. A VM that's running when you upgrade has no limit until its next start ([the QEMU wrapper](https://next.devvm.dev/docs/internals/processes/#the-qemu-wrapper-and-its-keeper)).
- **A forwarded port answers after a burst:** when the port forwarder runs out of open files while accepting a connection, it now tries again shortly after, and so do a link's socket and a browser login's forward, which also carries at most 16 connections at once. The forwarder used to stop accepting connections on that port while it still listened there, so the port took connections that nothing answered until the server in the VM restarted ([how it reaches the VM](https://next.devvm.dev/docs/internals/ports/#how-it-reaches-the-vm)).
- **A VM's proxy lets go of what a VM leaves:** a VM's proxy used to count only its tunnels toward its limit, keep idle connections open without end, keep a plain HTTP request running after its client had gone, and take 1 MiB of a request's headers inside an intercepted tunnel. It now:
  - holds at most 2048 of the VM's connections of every kind at once, where one without the VM's password doesn't count, and has at most 2048 requests to hosts under way at once
  - closes a connection that waits 10 minutes for its next request, or that lacked the VM's password
  - ends a plain HTTP request a minute after its client has stopped sending and nothing has come back
  - takes at most 64 KiB of headers everywhere, and carries at most 100 HTTP/2 requests at once in a tunnel
  - lets long downloads, WebSockets and slow streams go on as long as they last ([the proxy](https://next.devvm.dev/docs/internals/network/#the-proxy))
- **A plain `ws://` WebSocket connects through the proxy,** where it used to get `502` ([the proxy](https://next.devvm.dev/docs/internals/network/#the-proxy)).
- **A `NO_PROXY` entry with port 0 matches nothing:** an entry whose port no request has, such as `git.test:0`, or whose port isn't in plain decimal, now matches no host, as one past 65535 already didn't. The proxy used to read `git.test:0` as `git.test` on every port, so it sent those hosts directly instead of through your company proxy, and it read `git.test:080` or `git.test:+80` as port 80, which Go's clients don't ([through a company proxy](https://next.devvm.dev/docs/internals/network/#through-a-company-proxy)).
- **`.git/config` no longer seems to lose its pin on Linux hosts:** when git on this machine replaces `.git/config` just as devvm pins it again, devvm now pins the file that the rename left, and warns only that it was pinned again. The pin used to fail then, and devvm warned that the file lost its pin and couldn't be pinned again, then that it was pinned again, at the VM's next check, and a VM's start could fail the same way ([how a Linux host locks .git](https://next.devvm.dev/docs/internals/git-protection/#on-linux-hosts)).
- **A stopped forwarder or link session takes its ssh with it:** each signal that devvm sends a VM's port forwarder or link session now also reaches what the process started, and either one stops its ssh before it exits. devvm stopping either one, or a `kill` of either, used to leave its ssh connection to the VM running on this machine, with its control socket in devvm's run folder. `devvm gc --orphans` also deletes a forwarder's socket that nothing listens on ([how devvm starts them](https://next.devvm.dev/docs/internals/processes/#how-devvm-starts-them)).
- **A name fails at once with transparent mode off:** in a VM confined to its proxy, with transparent mode off or stopped, the VM's programs now ask the VM's own name server, at `127.0.0.1`, directly, from each VM's next launch, so a lookup through the system's resolver, such as `getent`'s or curl's, fails at once. On a Linux host, such a lookup used to wait out its timeout, because systemd-resolved's stub kept retrying a name server where nothing listened, and workerd under `wrangler dev` waited about 40 seconds for each lookup, which now also fails at once. A VM on the open tier keeps systemd-resolved's stub ([the VM's resolver](https://next.devvm.dev/docs/internals/network/#the-vms-resolver)).
- **A Nix package is downloaded once:** devvm now looks in the shared Nix cache again before it downloads a package. When two requests for a package that wasn't in the cache yet came close together, the second could download it again after the first had kept it, and the cache counted it twice against its cap ([the shared Nix cache](https://next.devvm.dev/docs/internals/network/#the-shared-nix-cache)).
- **A refused launch leaves a running VM running:** on a launch or a `devvm network` change, devvm now checks the company proxy, your CAs, the VM's CA and its secret files before it stops the VM's proxy, and when it refuses, it says it left the VM and its proxy running as they were. `devvm restart` checks the company proxy and your CAs before it stops the VM. When `config.toml`'s proxy named a user and no `proxy` secret was saved, `devvm` in the folder of a running VM used to refuse, as it should, but also stop the VM, and `devvm restart` stopped it before it refused. The same happened when your CAs folder couldn't be used, or the VM's CA or secret files couldn't be readied ([the proxy](https://next.devvm.dev/docs/internals/network/#the-proxy)).
- **A VM never runs on without its proxy:** a `devvm network` change between `internet`, `allowlist` and `none` on a running VM is refused before the VM's tier changes, so its tier never says one thing while its proxy enforces another. A VM whose proxy doesn't enforce the tier the VM has now, or whose proxy is stopped for new settings and then can't start again, is still stopped. A `devvm network` change now stops it in that case as well, where it used to leave the VM running without its proxy ([the proxy](https://next.devvm.dev/docs/internals/network/#the-proxy)).
- **A VM's logs are held to their caps:** while a VM runs, its proxy now keeps the disk space that Lima's console log for the VM and Lima's own logs for the VM each take under 10 MiB, with a `.1` file of up to 10 MiB more, and replaces the VM's proxy password in them as they grow. Root in a VM could write to its serial console, `/dev/hvc0`, without end, and the console log grew until this machine's disk was full, and so could Lima's own logs for the VM until its next start. A VM that's running when you upgrade gets this once a devvm command starts its proxy again ([Lima's hostagent](https://next.devvm.dev/docs/internals/processes/#limas-hostagent)).
- **devvm's other logs are held to their caps as well:**
  - The port forwarder's and the link session's logs now stay under 1 MiB while they run, not only from their next start, and a link's warnings take turns with the session's other lines.
  - The build proxy's log stays under 10 MiB, as a VM's proxy's does.
  - A run writes at most 128 MiB to its run log, and the run logs take at most 256 MiB together, though devvm never deletes the newest or one that a running devvm still writes ([the run log](https://next.devvm.dev/docs/internals/overview/#the-run-log)).
- **devvm desktop goes on after a burst:** when `devvm desktop`'s relay runs out of open files while accepting a viewer, it now tries again shortly, as the port forwarder does. `devvm desktop` used to end with an error, and the desktop's port with it ([the desktop relay](https://next.devvm.dev/docs/internals/processes/#the-desktop-relay)).
- **A VM's size that isn't a number is refused:** when a VM's state file holds a size devvm can't read as a number, such as `"cpus": "four"` after an edit by hand, devvm now refuses to start the VM or show its size, names the value, and says to set it again with `devvm size`. The VM used to start with the image's size without a word. `--cpus`, `--memory`, `--disk`, `config.toml` and `devvm size -g` also refuse a number too big for devvm to read, which for a disk reached Lima as infinity ([size](https://next.devvm.dev/docs/using/ports-size/#size)).

### Breaking

- **Pins in your own layers:** a layer of yours can pin a download for each architecture and fetch the right one with `devvm-fetch "$URL" "$(devvm_sha TOOL)" OUT`, as devvm's own scripts do ([the example](https://next.devvm.dev/docs/using/customizing/#example-mailpit)).

### Fixed

- **dotnet on the allowlist tier** can reach DigiCert's OCSP responder, `ocsp.digicert.com` on port 80, which NuGet asks when it can't fetch DigiCert's revocation list ([dotnet](https://next.devvm.dev/docs/using/toolchains/#dotnet)).

## 0.1.0

Released 2026-11-06.

The first release of devvm, which gives each project folder an isolated VM of its own, ready for you or a coding agent to work in. It runs on macOS 13 or newer and on Linux, on arm64 and x86_64, with Lima 2.0 or newer. It's tested on Apple silicon Macs and on Linux on both arm64 and x86_64, but not yet on Intel Macs.

- **A VM for each project folder:** running `devvm` in a folder makes its VM, or opens the one it has, and gives you a shell in it at the same path as on your machine. The VM mounts only that folder read-write, and with `--clone` it gets a clone of the repo of its own instead, whose work you fetch with `git fetch devvm`.
- **Ready in seconds:** every VM is a copy of a base image that devvm builds once, and the toolchains and coding agents are shared tools that VMs mount read-only. devvm detects node, python, rust and go from the project's files, and the built-in `docker`, `nix` and `desktop` layers, your own layers from `devvm layer new`, a project's `devcontainer.json` and `--from` with a container image change what a VM starts from.
- **Coding agents in the sandbox:** Claude Code, Codex and opencode run in the VM with your settings, skills and MCP servers. devvm keeps their settings and logins in a store of its own on your machine, `devvm agent import` copies them in from an agent you already use, `devvm agent login` makes an agent's login from the VM, and `devvm agent save` brings a VM's settings back to the store after you review the diff.
- **Network tiers and secrets:** every VM goes through a proxy that devvm runs for it, and its tier, which is open, internet, allowlist or none, decides what the proxy lets it reach. New VMs get the allowlist tier. On every tier, your secrets, such as your GitHub token and Claude Code token, stay on your machine, because the proxy puts them into the VM's requests.
- **`.git` protection:** on macOS, devvm locks a project's git hooks and config with a flag that even root in the VM can't clear, so code in the VM can't make your next git command on this machine run something.
- **Reaching VMs:** each running VM can be reached by name from ssh and from editors such as VS Code (`devvm code`), with your SSH agent only when you allow it. A VM forwards the ports you ask for, `devvm link` lets one VM reach a service that another VM publishes, and `devvm desktop` opens a VM's desktop in Screen Sharing on macOS, or serves it to a VNC viewer of your own on Linux.
- **Managing VMs and space:** `devvm ls`, `devvm stop`, `devvm restart`, `devvm update` and `devvm rm` manage VMs, and `devvm images`, `devvm gc`, `devvm space` and `devvm retention` show and clean up the images, shared tools and exports devvm keeps. devvm never deletes a project VM on its own, because it may hold unsaved work.
- **Installing and upgrading:** install devvm with Homebrew (`brew trust --formula devvmhq/tap/devvm`, then `brew install devvmhq/tap/devvm`) or with the install script, which checks the release's minisign signature and checksum and asks before it installs what devvm needs, such as Lima. `devvm doctor` checks this machine, and `devvm upgrade` installs a newer release once it has checked the signature.
- **For scripts:** many commands take `--json`, and `--no-input` makes devvm fail where it would ask, naming the flag that answers the question.
