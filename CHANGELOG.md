# Changelog

What's changed on `main` since the latest release is in [Unreleased](#unreleased), at the bottom of this page.

## 0.1.1-rc.3

A release candidate for 0.1.1, adding to 0.1.1-rc.2. Install it with `devvm upgrade --to 0.1.1-rc.3`, the install script's `--version 0.1.1-rc.3`, or `brew install devvmhq/tap/devvm-rc`. Homebrew's `devvm` stays on 0.1.0.

### Breaking

- **Your layers run after devvm's prelude:** devvm puts one line of its own in place of your layer's `#!` line, which gives the layer `$devvm_arch`, `$devvm_libc` and `devvm_sha`. A layer that sets its own `devvm_arch` or another `devvm_` name keeps its own. In a layer without a `#!` line, the line numbers in bash's errors are one more than the file's ([your own layers](https://next.devvm.dev/docs/using/customizing/#your-own-layers)).

### After you upgrade

- Base, every image built on it and every shared tool image are built again once, because base now has `git-lfs` and each build script starts with devvm's prelude on one line, which keeps the line numbers in a build's errors the script's own.
- Run `devvm update` in each existing VM's folder. Until you do, a VM made from an older image says it's outdated, and every existing VM says there are newer shared tools at the same versions. The first update or new VM builds each of its shared tools again, one at a time, which takes several minutes.
- An existing `--clone` VM gets `git-lfs` only once it's made again, with `devvm clone off`, then `devvm update`, then `devvm clone on`. Until then, its Git LFS files stay pointers.

### New

- **Cursor (#44, thanks to @barnesoir):** `--agents cursor` gives a VM Cursor's CLI, as `cursor-agent` or `agent`, and `devvm agent login cursor` logs it in from a browser on any machine, with the login kept on this machine ([Cursor CLI login](https://next.devvm.dev/docs/using/coding-agents/#cursor-cli-login)). `devvm cursor` opens the folder's VM in the Cursor editor, as `devvm code` does in VS Code. Recent Cursor runs its Agent in the VM with your Cursor sign-in in memory, so `devvm cursor` warns unless your Cursor settings send Agent's requests through the app on this machine, and you should open only VMs you trust with it ([Cursor's Agent](https://next.devvm.dev/docs/using/ssh/#cursors-agent)).
- **`devvm paste` (#38, thanks to @DustyPolk):** sends the image, PDF or file you copied on this machine into the running VM and puts its path in the VM on your clipboard, so you can paste it into a coding agent. A copied file goes only after you say yes, and `devvm paste rm` deletes what it sent ([pasting images](https://next.devvm.dev/docs/using/coding-agents/#pasting-images)).
- **`devvm agent import` can follow your dotfiles' links:** a link out of an agent's folder, such as `~/.claude/skills/x` into a dotfiles repo, is copied when you say yes in a terminal, when you pass `--follow-links`, or when it leads into a folder that `config.toml`'s `follow-links` names, such as `["~/dotfiles"]`. The store gets copies, never links, and devvm never follows a link to your home folder, its own folders, places that hold secrets, such as `~/.ssh`, or an agent's logins or history ([links out of an agent's folder](https://next.devvm.dev/docs/using/coding-agents/#links-out-of-an-agents-folder)).
- **`--clone` copies your repo as it is here:** the VM's clone gets every branch, tag and remote-tracking branch, a detached HEAD, what you've staged and what you haven't, a rebase, merge or other operation in progress, and your stash. It also gets your remotes without credentials, the repo's hooks and its own settings, your initialised submodules, each with a clone of its own, and the Git LFS objects your checked-out files point to, as every VM now has `git-lfs`. A partial clone is copied with the objects it has, and the VM's git fetches the rest from its remote. Untracked and ignored files, such as `.env`, and credential helpers stay on this machine, and devvm names anything it leaves out that you'd expect in the VM. Because `origin` is real in the VM, code there that may use your GitHub token can push to it, which a network rule can stop ([what's copied](https://next.devvm.dev/docs/using/clone/#whats-copied), [the settings](https://next.devvm.dev/docs/using/clone/#the-settings), [submodules](https://next.devvm.dev/docs/using/clone/#submodules), [a partial clone](https://next.devvm.dev/docs/using/clone/#a-partial-clone), [Git LFS](https://next.devvm.dev/docs/using/clone/#git-lfs)).
- **All of a `--clone` VM's work comes back:** `devvm clone fetch` also saves commits that only the VM's detached HEAD has as `saved/devvm/HEAD` and the VM's stash entries as `saved/devvm/stash-N`, and it brings back each submodule's branches and the LFS objects the VM's work points to, without `git-lfs` on this machine. `devvm rm` and `devvm clone off` check all of these and ask before any of them goes ([deleting the VM](https://next.devvm.dev/docs/using/clone/#deleting-the-vm)).
- **Pins in your own layers:** a layer of yours can pin a download for each architecture and fetch the right one with `devvm-fetch "$URL" "$(devvm_sha TOOL)" OUT`, as devvm's own scripts do ([the example](https://next.devvm.dev/docs/using/customizing/#example-mailpit)).
- **Quiet hosts:** Cursor CLI's metrics host, `api3.cursor.sh`, and Go's `telemetry.go.dev` stay blocked, but their blocks no longer show before the VM's prompt, in `devvm-why` or in `devvm network lock`. `devvm network log` still lists them, each line ending `, quiet` ([quiet hosts](https://next.devvm.dev/docs/safety/network/#quiet-hosts)).

### Changed

- **`--clone` in a folder of repos or a git worktree** copies each repo as above. A worktree's clone also gets the repo's default branch, remote-tracking branches and tags, and devvm says that the repo's other local branches stay on this machine.
- **`--clone` refuses a repo with a grafts file** before it makes the VM, and says what to do ([requirements](https://next.devvm.dev/docs/using/clone/#requirements)).
- **The proxy counts more addresses as internal:** a 6to4 address, in `2002::/16`, is judged by the IPv4 address in it, as a NAT64 address is, so `2002:a00:1::1` is as private as `10.0.0.1`. A deny for an IPv4 address also covers its 6to4 form, but an allow doesn't, because anyone may run a 6to4 relay. Teredo, IPv6's and IPv4's documentation ranges and other special ranges are refused unless a rule names the address, and `--from`'s registries are judged by the same list ([the proxy](https://next.devvm.dev/docs/internals/network/#the-proxy)).
- **Pins:** base's mise is 2026.11.8, Docker's buildx is 0.39.0 and compose 5.7.1, and Nix is 2.35.6.

### Fixed

- **`--clone` of a shallow or SHA-256 repo (#40):** a repo from `git clone --depth 1` or one that uses SHA-256 failed after devvm made the VM. Both work now, and a VM whose copy failed gets its clone the next time you run devvm in its folder. Thanks to @Josuesp1620 for the report and @dhruv1220 for finding the cause in #42 ([a copy that didn't finish](https://next.devvm.dev/docs/using/clone/#a-copy-that-didnt-finish)).
- **A stopped VM no longer keeps its listed ports from other VMs:** only a running VM holds a port. When the first VM starts again, devvm and `devvm ports` say that the other VM has the port, and the first VM takes it back within about 20 seconds of the other one stopping. Meanwhile, both VMs' apps share that port's site data and service workers in your browser ([two VMs and one port](https://next.devvm.dev/docs/using/ports-size/#two-vms-and-one-port)).
- **`devvm ports` says why a listed port isn't forwarded,** such as the forwarder's limit of 256 ports or Linux refusing a port below 1024, instead of always blaming a program on this machine ([a listed port isn't forwarded](https://next.devvm.dev/docs/using/troubleshooting/#a-listed-port-isnt-forwarded)). When a port's forward ends, so do its connections ([how it reaches the VM](https://next.devvm.dev/docs/internals/ports/#how-it-reaches-the-vm)).
- **A name that doesn't resolve says why:** a block now says whether this machine's DNS has no address for the name or didn't answer in time, and after a failure that may pass, the proxy asks once more before it blocks the name ([log files](https://next.devvm.dev/docs/internals/network/#log-files)).
- **dotnet on the allowlist tier** can reach DigiCert's OCSP responder, `ocsp.digicert.com` on port 80, which NuGet asks when it can't fetch DigiCert's revocation list ([dotnet](https://next.devvm.dev/docs/using/toolchains/#dotnet)).
- **`devvm history import FILE`** takes a `.tar.gz` made with macOS's `tar`, leaving out its AppleDouble `._` files ([importing history](https://next.devvm.dev/docs/using/coding-agents/#importing-history)).
- **opencode's links at `devvm agent import`** are copied or named as the other agents' are, where they were dropped without a word ([importing from this machine](https://next.devvm.dev/docs/using/coding-agents/#importing-from-this-machine)).

## 0.1.1-rc.2

A release candidate for 0.1.1, adding to 0.1.1-rc.1. Install it with `devvm upgrade --to 0.1.1-rc.2`, the install script's `--version 0.1.1-rc.2`, or `brew install devvmhq/tap/devvm-rc`. Homebrew's `devvm` stays on 0.1.0.

### After you upgrade

- Base and every image built on it are built again once, for transparent mode's programs.
- Run `devvm update` in an existing VM's folder to give it transparent mode, which new VMs get by default: its image predates the programs it needs.
- On a Linux host, run `devvm mount-cache none` for each existing VM, to stop the 9p cache bug below. Each launch reminds you until you do.
- If you used `devvm git-protect strict`, use `devvm clone on` for code you don't trust: strict is gone.
- Make new API keys for any VM you don't trust that had keys passed to it as they were.

### New

- **Transparent mode (#35), on by default:** on every tier but open, tools that ignore the proxy settings, such as `wrangler dev`, static Go binaries and containers, reach the VM's proxy and its allowlist anyway. A VM made before needs `devvm update` first, and `devvm network transparent off` turns it off for a VM ([what it covers](https://next.devvm.dev/docs/safety/network/#tools-that-ignore-the-proxy)).
- **Folders of repos with `--clone` (#3):** one VM gets a clone of each repo you pick, at the same paths. `devvm clone fetch` brings back every repo's work, and `devvm clone add PATH` adds one ([folders of repos](https://next.devvm.dev/docs/using/clone/#folders-of-repos)).
- **Rules by HTTP method and path:** `--method` and `--path` on `devvm network allow`, `deny` and `rm`, such as `devvm network deny api.github.com --method POST,PUT,PATCH,DELETE`.
- **Your own secrets:** `devvm secret set NAME --host HOST --env VARIABLE`, then `devvm secret use NAME`. The VM only ever sees a placeholder, and `--method` and `--path` limit where the real value goes.
- **Learning a VM's hosts (#17):** `--network learn`, then `devvm network lock` to keep the hosts you choose.
- **`.git` protection on Linux (#4, #20):** `.git` is locked read-only around QEMU, without root. Where a host can't, such as Ubuntu with AppArmor, devvm watches `.git`, warns at each launch, and names what changed.
- **Nested repos (#3):** a VM protects the `.git` of each repo up to 4 folders down. `devvm doctor` suggests `safe.bareRepository explicit`.
- **pi and more providers (#23, #31, #32):** pi is a fourth agent, and Gemini, Groq, Mistral, xAI and DeepSeek keys stay on this machine.
- **Prereleases on Homebrew (#19):** `brew install devvmhq/tap/devvm-rc`.

### Changed

- **The 9p cache on Linux (#36):** Lima's default cache could write files to this machine empty or cut short, and made SQLite and Gradle fail. New Linux VMs use `none`, and `devvm mount-cache none` switches existing ones. Under `none`, keep SQLite WAL databases and other files that programs map for writing on the VM's own disk, or use `--clone`. macOS doesn't change.
- **A `--clone` VM in a folder another VM mounts** is refused, and `devvm rm` asks before deleting one made earlier.
- **Logins:** a VM's copy of Codex's and Claude Code's login files keeps only the fields devvm knows. opencode, like pi, gets no key devvm doesn't bind, unless you list the provider in `config.toml`'s `[pass-keys]` (#30).
- **Warnings** print once per command.
- **Nix** is 2.35.5.

### Removed

- **`devvm git-protect strict` (#37):** it couldn't keep git on this machine out of submodules the VM adds, so it's a usage error now. Strict VMs become `on`, and devvm takes out the `diff.ignoreSubmodules = all` it set, keeping a value of your own ([VMs that were strict](https://next.devvm.dev/docs/safety/git-protection/#vms-that-were-strict)).

### Fixed

- opencode's history copy with SQLite 3.54 (#26), a NUL byte in an ssh socket's path (#25), a build VM reusing its clone's ssh port, a login saved for an agent the VM lacks (#27), and `.git` protection locking a folder that only looks like a git folder (#28).

## 0.1.1-rc.1

A release candidate for 0.1.1, for trying the changes below before the release. Install it with `devvm upgrade --to 0.1.1-rc.1`, or with the install script's `--version 0.1.1-rc.1`. Homebrew stays on 0.1.0.

- **A dotnet toolchain:** the .NET SDK is a shared toolchain, chosen by a folder's `*.sln`, `*.slnx`, `*.csproj`, `*.fsproj` or `global.json`, and a `global.json`'s `sdk.version` picks the SDK. devvm downloads Microsoft's archive for each platform and checks its SHA-512, global tools and workloads go to the VM's home folder, and the .NET CLI's telemetry is off ([toolchains](https://next.devvm.dev/docs/using/toolchains/)).

When a certificate isn't trusted, devvm says so and points to the docs instead of saying to check the connection. On macOS, the CA also has to be trusted in the Keychain.
- **Release candidates:** devvm can ship prereleases, such as this one. `devvm upgrade --to` installs one, and devvm upgrade, the release check and the install script's default never pick one on their own.
- **Lima 2.2 or newer:** devvm needs Lima 2.2 at least, and it's tested with Lima 2.3. `devvm doctor` says when Lima is older.
- **Updated pins:** base's docker is 29.9.3, mise 2026.11.3, rustup 1.29.3, and tealdeer 1.9.1, with a newer oh-my-bash. The shared tools' backends are named, so mise's registry can't switch opencode to a source with no downloads. base installs ICU, which .NET needs, so base and every image built on it are built again once.

## 0.1.0

Released 2026-11-06.

The first release of devvm, which gives each project folder an isolated VM of its own, ready for you or a coding agent to work in. It runs on macOS 13 or newer and on Linux, on arm64 and x86_64, with Lima 2.0 or newer. It's tested on Apple silicon Macs and on Linux on both arm64 and x86_64, but not yet on Intel Macs.

- **A VM for each project folder:** running `devvm` in a folder makes its VM, or opens the one it has, and gives you a shell in it at the same path as on your machine. The VM mounts only that folder read-write, and with `--clone` it gets a clone of the repo of its own instead, whose work you fetch with `git fetch devvm`.
- **Ready in seconds:** every VM is a copy of a base image that devvm builds once, and the toolchains and coding agents are shared tools that VMs mount read-only. devvm detects node, python, rust and go from the project's files, and the built-in `docker`, `nix` and `desktop` layers, your own layers from `devvm layer new`, a project's `devcontainer.json` and `--from` with a container image change what a VM starts from.
- **Coding agents in the sandbox:** Claude Code, Codex and opencode run in the VM with your settings, skills and MCP servers. devvm keeps their settings and logins in a store of its own on your machine, `devvm agent import` copies them in from an agent you already use, `devvm agent login` makes an agent's login from the VM, and `devvm agent save` brings a VM's settings back to the store after you review the diff.
- **Network tiers and secrets:** every VM goes through a proxy that devvm runs for it, and its tier, which is open, internet, allowlist or none, decides what the proxy lets it reach. New VMs get the allowlist tier. On every tier, your secrets, such as your GitHub token and Claude Code token, stay on your machine, because the proxy puts them into the VM's requests.
- **`.git` protection:** on macOS, devvm locks a project's git hooks and config with a flag that even root in the VM can't clear, so code in the VM can't make your next git command on this machine run something.
- **Reaching VMs:** each running VM can be reached by name from ssh and from editors such as VS Code (`devvm code`), with your SSH agent only when you allow it. A VM forwards the ports you ask for, `devvm link` lets one VM reach a service that another VM publishes, and `devvm desktop` opens a VM's desktop in Screen Sharing on macOS, or serves it to a VNC viewer of your own on Linux.
- **Managing VMs and space:** `devvm ls`, `devvm stop`, `devvm restart`, `devvm update` and `devvm rm` manage VMs, and `devvm images`, `devvm gc`, `devvm space` and `devvm retention` show and clean up the images, shared tools and exports devvm keeps. devvm never deletes a project VM on its own, because it may hold unsaved work.
- **Installing and upgrading:** install devvm with Homebrew (`brew trust --formula devvmhq/tap/devvm`, then `brew install devvmhq/tap/devvm`) or with the install script, which checks the release's minisign signature and checksum and asks before it installs what devvm needs, such as Lima. `devvm doctor` checks this machine, and `devvm upgrade` installs a newer release once it has checked the signature.
- **For scripts:** many commands take `--json`, and `--no-input` makes devvm fail where it would ask, naming the flag that answers the question.

## Unreleased

These changes are on `main` and go out in the next release.

### Breaking

- **At most 17 VMs run at once:** each VM's ssh is now on one of the 17 ports from 1024 up that every browser refuses, so no page in your browser reaches a server in a VM through it. Root in a VM could make its ssh port answer as a web server, which got the cookies of the apps you use on `localhost`, even in a VM that forwards no ports. A start past 17 fails and names the VMs that run on those ports ([too many VMs at once](https://next.devvm.dev/docs/using/troubleshooting/#too-many-vms-at-once)).
- **A VM that forwards every port leaves out those 17:** a server in the VM on one of them, such as an X server on 6000, reaches this machine only when you list the port with `devvm ports`, so a VM can't take the ports other VMs' ssh needs. `devvm ports` and each launch warn when a VM's list names one of them ([ports](https://next.devvm.dev/docs/using/ports-size/#ports)).
- **A short host name no longer reaches a host through the proxy:** a tool in a VM that used a name such as `jenkins` for a host on your company's network now needs its full name, such as `jenkins.corp.example.com`, as the proxy no longer adds this machine's DNS search domain ([a name that doesn't resolve](https://next.devvm.dev/docs/using/troubleshooting/#a-name-that-doesnt-resolve)).
- **The agent store keeps only what a seed has of Claude Code's plugins:** if you imported Claude Code's settings with devvm 0.1.0, which copied your whole `~/.claude/plugins`, the first start of any VM takes your plugins' data, and the store's other entries of that folder that are this machine's own, such as `installed_plugins.json`, out of devvm's agent store, where every VM with Claude Code could read them, and warns once, naming them. Your own `~/.claude/plugins` is left as it is. A store whose plugins folder is a link, or below one, which only a store you made yourself has, now stops every VM with Claude Code from starting until it's a folder of its own, as a VM's mount would follow the link ([Claude Code's plugins](https://next.devvm.dev/docs/using/coding-agents/#claude-codes-plugins)).
- **`devvm agent import` and `devvm agent save` refuse a linked store:** when a folder on the way to what they write in devvm's agent store is a link, from `~/.config/devvm/agents` down, such as `~/.config/devvm/agents/claude` linked into a dotfiles repo, they now fail and name the link before they change anything. Before, they wrote through the link and took out whatever the folder it led to held that they didn't write, which for a link to your home folder deleted your files. Make that folder one of its own, then run the command again ([devvm's agent store](https://next.devvm.dev/docs/using/coding-agents/#devvms-agent-store)).

### After you upgrade

- A VM's proxy that runs as you upgrade keeps running as one process, without a sandbox, until the VM's next launch, which starts its two processes, as it starts a proxy again for every new devvm. Until then, `devvm doctor` names each VM whose proxy an older devvm started ([the proxy runs without a sandbox](https://next.devvm.dev/docs/using/troubleshooting/#the-proxy-runs-without-a-sandbox)).
- Each existing VM's ssh moves to one of the 17 ports that browsers refuse at the VM's next start, in the one change devvm makes to its Lima config, which gives the VM new ssh host keys, as any change to its Lima config does. A VM that runs as you upgrade keeps its old port until then, and devvm warns of it at each launch, so stop it with `devvm stop` in its folder, and its next start moves it ([too many VMs at once](https://next.devvm.dev/docs/using/troubleshooting/#too-many-vms-at-once)).
- A VM whose copy of an agent's settings file had `devvm-redacted` under a name you chose, such as a plugin's marketplace, gets the whole copy at its next launch, over its own. Until then, `devvm agent save` leaves that file out and warns, so make any change to it in devvm's agent store, or launch the VM again and make the change there.
- A VM that runs as you upgrade, with Claude Code's plugins imported by devvm 0.1.0, loses the store's entries that are this machine's own from its mount at the first start of any VM, so Claude Code there may not find the store's plugins until that VM's next launch. On a Linux host, it can keep seeing what it had read of them until its next start. If a plugin's data held a login of the plugin's own, every VM with Claude Code could read it, so sign in to that plugin again where you don't trust those VMs. Each VM gets its own `~/.claude/plugins` at its next launch, with no restart, in place of its link to the store's folder, and Claude Code started in a shell that was open before that launch finds none of the store's plugins, so start it in a new shell ([Claude Code's plugins](https://next.devvm.dev/docs/using/coding-agents/#claude-codes-plugins)).
- Each VM records its project folder's volume at its first launch that finds the folder. Until then, and for a VM whose folder was already gone before the upgrade, which never records one, a folder that moves while a restart gives its disk another device number still needs `devvm adopt VM`, and after a restart such a gone folder can still be called not connected ([a moved or renamed folder](https://next.devvm.dev/docs/using/vms/#a-moved-or-renamed-folder)).
- A VM that forwards an SSH agent and runs as you upgrade keeps the agent as it was, so it can still remove, lock or add keys, until its next start, and devvm warns of it each time it opens the VM or changes its links. Run `devvm restart` in its folder to give it the relay at once ([agent forwarding](https://next.devvm.dev/docs/using/ssh/#agent-forwarding)).

### Changed

- **Each VM's proxy runs as two processes:** `devvm _proxy` alone reads your Keychain, your agents' login files and your other files, and `devvm _proxy-child` reads the VM's network and asks `devvm _proxy` for each name's lookup and each connection, for a login's token exchange, and for each value bound to the VM as a request needs it. So the code that reads every byte a VM sends holds, besides the VM's own proxy password and CAs and your company proxy's password, only the values that the VM's own bindings name, each kept for a few minutes after it was last asked for. A new login's tokens, its refresh token among them, never reach the process that reads the VM's requests, and an error reply from an agent's token endpoint reaches the VM as it is up to 1 MiB, and gets `502` past that. A build's proxy writes its logs to a `logs/` folder of their own in its folder ([a VM's proxy](https://next.devvm.dev/docs/internals/processes/#a-vms-proxy)).
- **On macOS, the proxy's child runs in a macOS sandbox:** `devvm _proxy-child` starts under `sandbox-exec`, with a profile that lets it write only its VM's logs and the shared Nix cache and look at your policy files, so a bug that a VM drove there couldn't read your files, reach the Keychain or connect to this machine's unix sockets, such as ssh's and Docker's. If `sandbox-exec` is missing or fails to start it, the child runs without the sandbox, so the VM keeps its network, and `devvm doctor` warns for each VM whose proxy runs that way ([the proxy runs without a sandbox](https://next.devvm.dev/docs/using/troubleshooting/#the-proxy-runs-without-a-sandbox)).
- **On Linux, the proxy's child confines itself:** before it reads a byte of the VM's, `devvm _proxy-child` confines itself with Landlock and a seccomp filter, so a bug that a VM drove there could write and read only its VM's logs and the shared Nix cache, couldn't change any other file's mode, owner, attributes or times, run a program, or connect to a unix socket, such as an ssh master's, Docker's or your SSH agent's. It could still learn whether a file of yours exists, its size and when it changed. A kernel without Landlock or seccomp filters, or whose Landlock is older than ABI 6 or lacks its fix for signals between threads, confines the child only in part, and the VM keeps its network, and `devvm doctor` warns for each VM whose proxy runs that way, naming what the kernel lacks ([the proxy runs without a sandbox](https://next.devvm.dev/docs/using/troubleshooting/#the-proxy-runs-without-a-sandbox)).
- **The proxy's child connects only through `devvm _proxy`:** wherever its sandbox runs, on macOS and on Linux, it refuses the child every connection of its own, so `devvm _proxy` looks up each name for it and opens each connection, once its own read of your rules and this machine's addresses allows the address. So a bug that a VM drove in the child can't reach this machine's services on `localhost`, such as your dev servers, Docker's published ports and other VMs' proxies, nor this machine's own addresses or your LAN's private addresses, unless a rule names the address, just as the VM can't. A rule such as `devvm network allow 127.0.0.1:5432` still applies from the next connection, and a company proxy on `localhost` still works, though the child reaches whatever that company proxy reaches, as the VM does. Because `devvm _proxy` looks up its names, the child reads no file below `/etc` on Linux and doesn't talk to mDNSResponder on macOS ([the child's sandbox](https://next.devvm.dev/docs/internals/network/#the-childs-sandbox)).
- **`devvm doctor` checks every VM's state:** it reads each VM's `vm.json` and each of its sections as every command on a VM does, and warns of each VM whose state devvm can't read, naming the VM and why, the file included, without changing anything ([a file devvm can't read](https://next.devvm.dev/docs/using/troubleshooting/#a-file-devvm-cant-read)).
- **A marketplace's credential gets a warning:** when `devvm agent import` or `devvm agent save` copies a Claude Code marketplace that has a password or an access token in its clone's git config or its source in `known_marketplaces.json`, which every VM with Claude Code can read, it warns and names the marketplace, the store's file and the keys, and copies it as before ([mounts](https://next.devvm.dev/docs/using/coding-agents/#mounts)).
- **Pins:** Cursor's CLI is 2026.11.17-f532c45.

### Fixed

- **`devvm agent login claude --setup-token` shows Claude Code's address (#57):** the login in the VM got no terminal of its own, so `claude setup-token`, which draws full-screen, showed nothing and waited. When devvm runs in a terminal, an agent's login in the VM now gets one too, as devvm's shell does, so Claude Code shows the address to open and the prompt for its code. Without a terminal, `--setup-token` warns that the login may show nothing. On a terminal, Ctrl-C now goes to the agent's login in the VM, which ends, and devvm then says that the login ended or saved nothing ([Claude Code login](https://next.devvm.dev/docs/using/coding-agents/#claude-code-login)).
- **MCP servers' logins in a VM finish and stay (#62):** with your subscription's login, each launch and each `devvm agent login claude` wrote devvm's copy of the login over the VM's `~/.claude/.credentials.json`, where Claude Code also keeps its logins to MCP servers. So a login to an MCP server that you started with `/mcp` in a VM failed when devvm set the VM up again before it finished, such as when you ran devvm in its folder from another terminal, and one that finished was gone at the VM's next launch. devvm now replaces only the Claude login in that file and keeps the rest, so the MCP servers' logins you make in a VM stay in that VM, and they never reach this machine or another VM. With a Claude Code token, the VM's file stays as it is ([MCP servers' logins](https://next.devvm.dev/docs/using/coding-agents/#mcp-servers-logins)).
- **Your claude.ai connectors work in a VM (#61):** with your subscription's login, Claude Code in a VM couldn't use the connectors you added in claude.ai, because the VM's proxy put the login only into requests to `api.anthropic.com`, so those to `mcp-proxy.anthropic.com`, which carries the connectors' traffic, held the login's placeholder and were refused. From each VM's next launch, the proxy puts the login into those too, below `/v1/mcp/`, so a VM with Claude Code can use every connector you added, as Claude Code on this machine can, and code in the VM can read and act through them. Disconnect the ones you don't want VMs to use, or deny `mcp-proxy.anthropic.com` with `devvm network deny` ([your claude.ai connectors](https://next.devvm.dev/docs/safety/attack-vectors/#the-network)). A Claude Code token, from `claude setup-token` or in devvm's environment, still goes only to `api.anthropic.com` ([Claude Code login](https://next.devvm.dev/docs/using/coding-agents/#claude-code-login)).
- **A `NO_PROXY` address with a zone no longer goes direct (#59):** an IPv6 address with a zone in your company proxy's `NO_PROXY`, such as `fe80::1%eth0`, sent that address without its zone past the company proxy. Such an entry now matches nothing, as it does in Go's HTTP clients ([behind a company proxy](https://next.devvm.dev/docs/safety/network/#behind-a-company-proxy)).
- **Claude Code's plugins work in a VM (#56):** a VM's `~/.claude/plugins` was devvm's agent store's folder, mounted read-only, so everything Claude Code writes there failed, such as a plugin's data in `${CLAUDE_PLUGIN_DATA}`, installing a plugin and updating a marketplace. Each VM's `~/.claude/plugins` is now its own folder, and the store's plugins are Claude Code's read-only seed at `~/.claude/plugins-seed`, so the store's plugins load as before, a plugin keeps its data in the VM, and a plugin you install in a VM stays in that VM until `devvm agent save` copies it into the store. The save adds plugins to the store and never takes one out, and an export of a VM's history leaves its plugins folder out. A store that devvm 0.1.0's import filled keeps only what a seed has, as Breaking above says ([Claude Code's plugins](https://next.devvm.dev/docs/using/coding-agents/#claude-codes-plugins)).
- **A folder that moved across a restart keeps its VM:** a folder that moved while a restart gave its disk another device number wasn't recognised, so devvm made it a second VM, and the gone folder of a VM whose disk was renumbered was called not connected. Each VM now records its folder's volume, which no renumbering changes: its volume UUID on macOS, and the file system's own ID on Linux's ext4, Btrfs and ZFS. So devvm offers a moved folder its VM by its volume, inode and birth time, and calls a VM's gone folder gone, once the VM has recorded its volume, as After you upgrade says ([a moved or renamed folder](https://next.devvm.dev/docs/using/vms/#a-moved-or-renamed-folder)). A folder at the VM's own path whose disk was renumbered, but on another volume than the one recorded, such as a copy of the disk with a volume ID of its own mounted there, is another folder, so devvm gives it the VM only after `devvm adopt` ([a folder made again](https://next.devvm.dev/docs/using/vms/#a-folder-made-again)).
- **A link inside an agent's folder copies only a setting:** `devvm agent import` copied a link inside an agent's folder as the file it led to wherever that file was in the folder, so a link in `~/.claude/skills` or `~/.claude/plugins/cache` could put your history, `~/.claude/.credentials.json` or a plugin's data into the store, where every VM with the agent reads it. Such a link is now copied only when it leads to one of the settings the import copies, and any other is left out with a warning that names where it leads ([importing from this machine](https://next.devvm.dev/docs/using/coding-agents/#importing-from-this-machine)).
- **`devvm agent import` no longer copies your plugins' data into every VM:** it copied all of `~/.claude/plugins` into the store, so every VM with Claude Code got the data that your plugins keep on this machine, which can hold their own logins. It now copies only the marketplaces, their records and the plugins' cache, and `devvm agent save` copies only those from a VM ([importing from this machine](https://next.devvm.dev/docs/using/coding-agents/#importing-from-this-machine)).
- **An export can't put what an import leaves out into a VM:** `devvm history import` left out the agents' logins and the files devvm's setup writes by their names as an export wrote them, so an export that spelled one another way, such as `.claude/./settings.json` or `.claude//plugins`, got it into the VM's home. The import now refuses a name with a `.` or empty part, and deletes what it leaves out by its path once it's unpacked ([importing history](https://next.devvm.dev/docs/internals/agents/#importing-history)).
- **A project folder's VM works after your Mac restarts (#60):** macOS numbers its disks' devices in the order they appear at boot, so after a restart an unchanged folder could be on a device with another number. devvm then took the folder for another one, so every command on its VM refused it as made for an earlier folder at its path, a stopped VM's start refused it as replaced, and the next check of `.git` called it replaced. A folder at the same path, with no link on it and with the same inode and birth time, is now the same folder on whichever device it's on, and its VM's next start records it on that device before it mounts it, in the one change devvm makes to its Lima config. A folder that moved after a restart, before its VM started again, isn't offered the VM, so `devvm adopt VM` moves it ([one VM per folder](https://next.devvm.dev/docs/internals/security/#one-vm-per-folder)).
- **Names you choose in an agent's settings are no longer taken for secrets (#55):** devvm took a plugin, a marketplace or an MCP server whose name had `key`, `token`, `secret` or `passw` in it, such as `tokeneconomizer` or `secret-scanner`, for a secret, and put `devvm-redacted` in place of all its settings in the VM's copy. Claude Code then refused the VM's `settings.json` whole, so every plugin was off in the VM. devvm now knows the agents' tables of names, such as Claude Code's `extraKnownMarketplaces` and `mcpServers` and Codex's `marketplaces` and `hooks.state`, and judges only the fields under a name, so a server named `secret-scanner` keeps its command and still loses its `env` and its `apiKey`. Thanks to @jspiro for the report and @dhruv1220 for the tests' idea in #58 ([keys in settings files](https://next.devvm.dev/docs/internals/network/#keys-in-settings-files)).
- **A folder whose name has separators in a row gets a VM (#52):** a folder named `x--y`, `foo (copy)` or `C++ stuff` failed to get one, because devvm turned each character other than a letter or digit into its own dash, and Lima refuses a name with dashes in a row. Each run of them now becomes one dash, so `foo (copy)` gets `devvm-foo-copy-<hash>`, and the state such a folder's failed VM left is replaced when you run devvm there again. Thanks to @se6a for the report ([VM names](https://next.devvm.dev/docs/internals/backends/#vm-names)).
- **Lima's console logs no longer keep a VM's proxy password:** Lima's boot scripts write the VM's proxy settings, with the VM's own proxy password, to the VM's serial console, and Lima keeps that console in `serial.log`, `serialp.log` or `serialv.log` in the VM's folder in devvm's Lima home. devvm took the passwords out of Lima's `ha.stderr.log` only, so those logs kept the VM's password. devvm now replaces each password in them with as many `*` once the VM has started, as it does in `ha.stderr.log` ([the run log](https://next.devvm.dev/docs/internals/overview/#the-run-log)).
- **A short name no longer reaches a denied host under your search domain:** the proxy looked names up with this machine's DNS search domain, which macOS takes from the network's settings and Linux from `/etc/resolv.conf`. So with `api.corp.example.com` denied and `**` allowing the rest, a VM could reach that host as `api`, or `api.eu.corp.example.com` as `api.eu`, when either had a public address, because no rule judged the name the search domain made. The proxy now looks each name up as it's written, so a short name such as `jenkins` no longer reaches a host through the proxy, and a tool in the VM reaches a host on your network by its full name, such as `jenkins.corp.example.com`. When a name without a dot doesn't resolve, the block says to use its full name, and a block because a name doesn't resolve no longer suggests a `devvm network allow` command, which the name's rule already gives ([a name that doesn't resolve](https://next.devvm.dev/docs/using/troubleshooting/#a-name-that-doesnt-resolve)).
- **A VM can no longer take an SSH agent away from you or other VMs:** a VM that forwarded your agent or devvm's own could remove every key from it with `ssh-add -D`, lock it with a password of its own with `ssh-add -x`, or add keys to it, because `ssh-agent` answers every request a forwarded connection sends. Every VM that shares devvm's agent lost it then, and with your own agent, so did you. A VM now reaches its agent only through its proxy, which passes on listing keys, signing and binding a session to a host, and refuses everything else, so `ssh-add` in a VM can still list and use the keys, but not remove, lock or add them. The ssh entries for editors name the same socket, so an editor's connection gets the same agent as devvm's shell, the one the VM started with, and the entry of a VM started outside devvm, such as with `devvm limactl start`, forwards no agent. A VM that's running when you upgrade keeps the old behaviour until its next start, so restart it with `devvm restart` ([the SSH agents](https://next.devvm.dev/docs/internals/processes/#the-ssh-agents)).
- **A VM's host keys are pinned whatever its ports:** when other programs on this machine, such as your own dev servers, held every port a VM lists, or the VM forwarded none with `devvm ports none`, a start that went no further than starting the VM, such as `devvm clone fetch` on a stopped `--clone` VM, didn't pin the VM's ssh host keys. devvm's own ssh to the VM then failed until something else pinned them, so `devvm clone fetch` and `devvm rm`'s fetch failed with `clone_fetch_failed`. devvm now pins the keys each time it starts a VM, whatever the VM forwards, and a command that finds the VM running without them pins them first ([ssh into VMs](https://next.devvm.dev/docs/internals/security/#ssh-into-vms)).
- **A removed link's connections end with it:** devvm link rm used to stop a link's new connections but leave its open ones running. A target that never closed its end kept each of those connections' ssh processes on this machine, and one of the 256 connections a client's links carry at once, until the client or the target stopped. Removing a link now ends its open connections within a few seconds, and when a target starts again, the connections still open through its earlier start end too ([removing a link](https://next.devvm.dev/docs/using/links/#removing-a-link)).
- **An agent's settings file that's one string no longer crashes `devvm agent save`:** when an agent's settings file in the VM was a single JSON string holding a placeholder, `devvm agent save` crashed. It now puts the saved value back in it. A login file on this machine that holds only `null` is now refused as not a JSON object, where saving a Codex or opencode login made in a VM failed on it ([saving a VM's settings](https://next.devvm.dev/docs/using/coding-agents/#saving-a-vms-settings)).
- **A closed connection's ssh process ends:** when a VM never closed its end of a forwarded port's or a link's connection, that connection's ssh process stayed on this machine after the program here, or in the client, had closed its side. So a hostile VM could take all 256 connections that a forwarder or a client's links carry at once. Such an ssh process now ends once its client has closed and the VM has sent nothing for 30 seconds. A program that closes its side for writing and then waits for an answer, as `nc -N` does, keeps its connection only while the VM sends something at least every 30 seconds, the first byte included, so a slow query that takes longer than that to start answering is cut ([how it reaches the VM](https://next.devvm.dev/docs/internals/ports/#how-it-reaches-the-vm)).
- **A forwarded port answers on `::1` too:** when this machine briefly couldn't listen on a port's IPv6 address, such as when it ran out of open files, the forwarder forwarded the port on `127.0.0.1` alone until the server in the VM restarted. A client that connects only over IPv6, such as `http://[::1]:PORT` or a tool that doesn't fall back to `127.0.0.1`, then didn't reach the VM, and another program on this machine could take `::1` on that port and get those connections instead. The forwarder now tries the port again at the VM's next report and forwards it on both addresses. A machine that denies the forwarder `::1` alone, such as through a security module, still gets its ports on `127.0.0.1`, and the forwarder's log says so ([when it can't forward](https://next.devvm.dev/docs/internals/ports/#when-it-cant-forward)).
- **Every host is read as the proxy reads it:** a few of devvm's checks read a host in a way of their own. A name with a letter that isn't plain ASCII, such as the Kelvin sign, which Unicode's case folding turns into `k`, was taken as the ASCII name it folds into by `devvm secret set --host`, an MCP server's URL and a `NO_PROXY` entry, and `--from` took a registry's host with such a letter, or an address in brackets before a trailing dot such as `[::1].`, as one on the internet. The proxy refuses such a host, so now devvm secret set refuses it, an MCP server with one gets no secret, a `NO_PROXY` entry with one matches no host, `--from` doesn't take such a registry as public, and devvm network rm with it never removes the rule with the plain letter. The proxy also answers `400` to a host with brackets around anything but an IPv6 address, such as `[evil.com]:443`. A partial clone's warnings also read a remote's host without its trailing dot, so they name `example.com` rather than `example.com.`, and a remote at `localhost.` gets the same warning as one at `localhost` ([how the proxy reads a host](https://next.devvm.dev/docs/internals/network/#the-proxy)).
- **A VM can't fill a Linux host with processes:** on a Linux host, each connection that a VM confined to its proxy made to the proxy started a devvm process on this machine, with no limit, so a VM that opened connections without end could start thousands of them. devvm now carries at most 256 of a VM's connections to its proxy at once, and answers any past that with `503` before it reaches the proxy. A VM that's running when you upgrade has no limit until its next start ([the QEMU wrapper](https://next.devvm.dev/docs/internals/processes/#the-qemu-wrapper-and-its-keeper)).
- **A forwarded port answers after a burst:** when the port forwarder ran out of open files while accepting a connection, it stopped accepting connections on that port while it still listened there, so the port took connections that nothing answered until the server in the VM restarted. It now tries again shortly after, and so do a link's socket and a browser login's forward, which also carries at most 16 connections at once ([how it reaches the VM](https://next.devvm.dev/docs/internals/ports/#how-it-reaches-the-vm)).
- **A VM's proxy lets go of what a VM leaves:** a VM's proxy counted only its tunnels toward its limit, kept idle connections open without end, kept a plain HTTP request running after its client had gone, and took 1 MiB of a request's headers inside an intercepted tunnel. It now holds at most 2048 of the VM's connections of every kind at once, where one without the VM's password doesn't count, has at most 2048 requests to hosts under way at once, closes a connection that waits 10 minutes for its next request, or that lacked the VM's password, ends a plain HTTP request a minute after its client has stopped sending and nothing has come back, takes at most 64 KiB of headers everywhere, and carries at most 100 HTTP/2 requests at once in a tunnel. A plain `ws://` WebSocket through the proxy, which got `502`, now connects. Long downloads, WebSockets and slow streams go on as long as they last ([the proxy](https://next.devvm.dev/docs/internals/network/#the-proxy)).
- **A `NO_PROXY` entry with port 0 matches nothing:** the proxy read an entry such as `git.test:0` as `git.test` on every port, so it sent those hosts directly rather than through your company proxy, and it read `git.test:080` or `git.test:+80` as port 80, which Go's clients don't. An entry whose port no request has, or whose port isn't in plain decimal, now matches no host, as one past 65535 already didn't ([through a company proxy](https://next.devvm.dev/docs/internals/network/#through-a-company-proxy)).
- **No false lost pin on Linux hosts:** when git on this machine replaced `.git/config` just as devvm pinned it again, the pin could fail, and devvm warned that the file lost its pin and couldn't be pinned again, then that it was pinned again, at the VM's next check. A VM's start could fail the same way. devvm now pins the file the rename left, and warns only that it was pinned again ([how a Linux host locks .git](https://next.devvm.dev/docs/internals/git-protection/#on-linux-hosts)).
- **A stopped forwarder or link session takes its ssh with it:** devvm stopping a VM's port forwarder or link session, or a `kill` of either, could leave its ssh connection to the VM running on this machine, with its control socket in devvm's run folder. Each signal devvm sends now reaches what the process started too, either one stops its ssh before it exits, and `devvm gc --orphans` also deletes a forwarder's socket that nothing listens on ([how devvm starts them](https://next.devvm.dev/docs/internals/processes/#how-devvm-starts-them)).
- **A name fails at once with transparent mode off:** in a VM confined to its proxy, with transparent mode off or stopped, a lookup through the system's resolver, such as `getent`'s or curl's, could wait out its timeout rather than fail at once, seen on a Linux host, because systemd-resolved's stub kept retrying a name server where nothing listened. The VM's programs now ask that name server, its own `127.0.0.1`, directly, from each VM's next launch, so workerd under `wrangler dev`, which waited about 40 seconds for each lookup on a Linux host, fails at once too, and a VM on the open tier keeps systemd-resolved's stub ([the VM's resolver](https://next.devvm.dev/docs/internals/network/#the-vms-resolver)).
- **A Nix package is downloaded once:** when two requests for a package that wasn't in the shared Nix cache yet came close together, the second could download it again after the first had kept it, and the cache counted it twice against its cap. It now looks in the cache again before it downloads ([the shared Nix cache](https://next.devvm.dev/docs/internals/network/#the-shared-nix-cache)).
- **A refused launch leaves a running VM running:** when `config.toml`'s proxy named a user and no `proxy` secret was saved, `devvm` in the folder of a running VM refused, as it should, but also stopped the VM, and `devvm restart` stopped it before it refused. The same happened when your CAs folder couldn't be used, or the VM's CA or secret files couldn't be readied. On a launch or a `devvm network` change, devvm now checks the company proxy, your CAs, the VM's CA and its secret files before it stops the VM's proxy, and says it left the VM and its proxy running as they were. `devvm restart` checks the company proxy and your CAs before it stops the VM. A `devvm network` change between `internet`, `allowlist` and `none` on a running VM is refused before the VM's tier changes, so its tier never says one thing while its proxy enforces another. A VM whose proxy doesn't enforce the tier the VM has now, or whose proxy is stopped for new settings and then can't start again, is still stopped, because a VM never runs on without its proxy. A `devvm network` change now stops it in that case too, where it left the VM running without its proxy ([the proxy](https://next.devvm.dev/docs/internals/network/#the-proxy)).
- **A VM's logs are held to their caps:** root in a VM could write to its serial console, `/dev/hvc0`, without end, and Lima's console log for the VM grew until this machine's disk was full, and so could Lima's own logs for the VM until its next start. While a VM runs, its proxy now keeps the disk space each of those logs takes under 10 MiB, on a file system with holes such as APFS or ext4, moving its end to the same name with `.1` added, of up to 10 MiB more, with any password in it replaced. It also replaces the VM's proxy password as the logs grow, so a reboot inside the VM, which on Linux hosts writes it to the console's log again, can't leave it there. A VM that's running when you upgrade gets this once a devvm command starts its proxy again. The port forwarder's and the link session's logs now stay under 1 MiB while they run, not only from their next start, a link's warnings take turns with the session's other lines, the build proxy's log stays under 10 MiB as a VM's proxy's does, a run writes at most 128 MiB to its run log, and the run logs take at most 256 MiB together, though devvm never deletes the newest or one that a running devvm still writes ([Lima's hostagent](https://next.devvm.dev/docs/internals/processes/#limas-hostagent)).
- **devvm desktop goes on after a burst:** when `devvm desktop`'s relay ran out of open files while accepting a viewer, `devvm desktop` ended with an error, and the desktop's port with it. It now tries again shortly, as the port forwarder does ([the desktop relay](https://next.devvm.dev/docs/internals/processes/#the-desktop-relay)).
- **A VM's size that isn't a number is refused:** when a VM's state file held a size devvm couldn't read as a number, such as `"cpus": "four"` after an edit by hand, the VM started with the image's size without a word. devvm now refuses to start the VM or show its size, names the value, and says to set it again with `devvm size`. `--cpus`, `--memory`, `--disk`, `config.toml` and `devvm size -g` also refuse a number too big for devvm to read, which for a disk reached Lima as infinity ([size](https://next.devvm.dev/docs/using/ports-size/#size)).
