# Changelog

What's changed on `main` since the latest release is in [Unreleased](#unreleased), at the bottom of this page.

## 0.2.0-rc.1

This is a release candidate for 0.2.0, and it adds to 0.1.1-rc.3. 0.2.0 takes 0.1.1's place, because its breaking changes need a new minor version. Install it with `devvm upgrade --to 0.2.0-rc.1`, the install script's `--version 0.2.0-rc.1`, or `brew install devvmhq/tap/devvm-rc`. Homebrew's `devvm` stays on 0.1.0.

Each change below links its section on [the 0.2.0 page](https://next.devvm.dev/docs/releases/0.2.0/), which has its full story, and the commit that made it.

### Breaking

- **At most 17 VMs run at once:** each VM's ssh now uses one of the 17 ports from 1024 up that every browser refuses, so no page in your browser reaches a server in a VM through that port. A start past 17 fails and names the VMs that run on those ports, so stop one of them first ([too many VMs at once](https://next.devvm.dev/docs/using/troubleshooting/#too-many-vms-at-once), [details](https://next.devvm.dev/docs/releases/0.2.0/#at-most-17-vms-run-at-once), [e4ea123](https://github.com/devvmhq/devvm/commit/e4ea123927cc90022b5333ab15e38f75c69c876a)).
- **A VM that forwards every port leaves out those 17 ports:** a server in the VM on one of them, such as an X server on 6000, reaches this machine only when you list its port with `devvm ports`, and `devvm ports` and each launch warn when a VM's list names one of them ([ports](https://next.devvm.dev/docs/using/ports-size/#ports), [details](https://next.devvm.dev/docs/releases/0.2.0/#at-most-17-vms-run-at-once), [e4ea123](https://github.com/devvmhq/devvm/commit/e4ea123927cc90022b5333ab15e38f75c69c876a)).
- **A short host name no longer reaches a host through the proxy:** a tool in a VM that reached a host on your company's network by a name such as `jenkins` now needs the host's full name, such as `jenkins.corp.example.com`, because the proxy no longer adds this machine's DNS search domain ([a name that doesn't resolve](https://next.devvm.dev/docs/using/troubleshooting/#a-name-that-doesnt-resolve), [details](https://next.devvm.dev/docs/releases/0.2.0/#names-are-looked-up-as-theyre-written), [c872cfe](https://github.com/devvmhq/devvm/commit/c872cfe66c349533820c885b2ed11b5db617fc24)).
- **The agent store keeps only what a seed has of Claude Code's plugins:** if you imported Claude Code's settings with devvm 0.1.0, which copied your whole `~/.claude/plugins`, the first start of any VM takes your plugins' data out of devvm's agent store, along with the folder's other entries that are this machine's own, such as `installed_plugins.json`. It warns once, naming what it took, and it leaves your own `~/.claude/plugins` as it is. If the store's plugins folder is a link, or below one, no VM with Claude Code starts until you make it a folder of its own ([Claude Code's plugins](https://next.devvm.dev/docs/using/coding-agents/#claude-codes-plugins), [details](https://next.devvm.dev/docs/releases/0.2.0/#claude-codes-plugins-in-the-agent-store), [7cc0dd7](https://github.com/devvmhq/devvm/commit/7cc0dd76edc858fea9afc90d71cbba8ac6f50f37)).
- **`devvm agent import` and `devvm agent save` refuse a linked store:** they now fail before they change anything, naming the link, when a folder on the way to what they write in devvm's agent store is a link, from `~/.config/devvm/agents` down, such as `~/.config/devvm/agents/claude` linked into a dotfiles repo. Make that folder one of its own, then run the command again ([devvm's agent store](https://next.devvm.dev/docs/using/coding-agents/#devvms-agent-store), [details](https://next.devvm.dev/docs/releases/0.2.0/#a-linked-agent-store-is-refused), [d939d1d](https://github.com/devvmhq/devvm/commit/d939d1d870cc0216b5a3036636b13489a869b71e)).

### After you upgrade

- Run `devvm update` in each existing VM's folder. The new mise and Docker change what goes into the images, so until you do, a VM made from an older image says it's outdated, and every existing VM says there are newer shared tools at the same versions. The first update or new VM builds base and each of its shared tools again, one at a time, which takes several minutes ([details](https://next.devvm.dev/docs/releases/0.2.0/#pins), [c9005ae](https://github.com/devvmhq/devvm/commit/c9005ae4be13f6ebe337111bdba980c3f595c7fe)).
- Each existing VM's ssh moves to one of the 17 ports that browsers refuse at the VM's next start, which gives the VM new ssh host keys. A VM that runs as you upgrade keeps its old port until then, and devvm warns of it at each launch, so run `devvm stop` in its folder, and its next start moves it ([too many VMs at once](https://next.devvm.dev/docs/using/troubleshooting/#too-many-vms-at-once), [details](https://next.devvm.dev/docs/releases/0.2.0/#at-most-17-vms-run-at-once), [e4ea123](https://github.com/devvmhq/devvm/commit/e4ea123927cc90022b5333ab15e38f75c69c876a)).
- A VM's proxy that runs as you upgrade stays one process, without a sandbox, until the VM's next launch, which starts it again as two processes. Until then, `devvm doctor` names each VM whose proxy an older devvm started ([the proxy runs without a sandbox](https://next.devvm.dev/docs/using/troubleshooting/#the-proxy-runs-without-a-sandbox), [details](https://next.devvm.dev/docs/releases/0.2.0/#each-vms-proxy-runs-as-two-processes), [aeea313](https://github.com/devvmhq/devvm/commit/aeea3135b27e0de898a449adb63b7742126b8ddb)).
- A VM that forwards an SSH agent and runs as you upgrade keeps the agent as it was until its next start, so it can still remove, lock or add keys, and devvm warns of it each time it opens the VM or changes its links. Run `devvm restart` in its folder to give it the relay at once ([agent forwarding](https://next.devvm.dev/docs/using/ssh/#agent-forwarding), [details](https://next.devvm.dev/docs/releases/0.2.0/#a-vm-and-its-ssh-agent), [19f9900](https://github.com/devvmhq/devvm/commit/19f9900b8633108cf69b28ee7a253b08bafff70f)).
- If you imported Claude Code's plugins with devvm 0.1.0 and a plugin's data held a login of the plugin's own, every VM with Claude Code could read that login, so sign in to that plugin again where you don't trust those VMs ([details](https://next.devvm.dev/docs/releases/0.2.0/#claude-codes-plugins-in-the-agent-store), [7cc0dd7](https://github.com/devvmhq/devvm/commit/7cc0dd76edc858fea9afc90d71cbba8ac6f50f37)).
- A VM that runs as you upgrade, with Claude Code's plugins imported by devvm 0.1.0, loses the store's entries that are this machine's own from its mount at the first start of any VM, so Claude Code there may not find the store's plugins until that VM's next launch. On a Linux host, the VM can keep seeing what it had read of them until its next start ([details](https://next.devvm.dev/docs/releases/0.2.0/#claude-codes-plugins-in-the-agent-store), [7cc0dd7](https://github.com/devvmhq/devvm/commit/7cc0dd76edc858fea9afc90d71cbba8ac6f50f37)).
- Each VM gets its own `~/.claude/plugins` at its next launch, without a restart, in place of its link to the store's folder. Claude Code started in a shell that was open before that launch finds none of the store's plugins, so start it in a new shell ([Claude Code's plugins](https://next.devvm.dev/docs/using/coding-agents/#claude-codes-plugins), [details](https://next.devvm.dev/docs/releases/0.2.0/#claude-codes-plugins-in-a-vm), [e97db05](https://github.com/devvmhq/devvm/commit/e97db057fd93873a14b075e7d46615dc2d020ac4)).
- If a VM's copy of an agent's settings file had `devvm-redacted` under a name you chose, such as a plugin's marketplace, the VM's next launch writes the whole copy over the VM's own. Until then, `devvm agent save` leaves that file out and warns, so make any change to it in devvm's agent store, or launch the VM again and make the change there ([details](https://next.devvm.dev/docs/releases/0.2.0/#names-you-choose-in-an-agents-settings), [f384829](https://github.com/devvmhq/devvm/commit/f3848294d8e1095f115ae13e224697484b38c47c)).
- Each VM records its project folder's volume at its first launch that finds the folder. Until then, a folder that moves while a restart gives its disk another device number still needs `devvm adopt VM`, and after a restart, the VM's gone folder can still be called not connected. Both stay true for a VM whose folder was already gone before the upgrade, because it never records a volume ([a moved or renamed folder](https://next.devvm.dev/docs/using/vms/#a-moved-or-renamed-folder), [details](https://next.devvm.dev/docs/releases/0.2.0/#a-folder-moved-across-a-restart), [ba510ee](https://github.com/devvmhq/devvm/commit/ba510eec1f55a7cd656050eabe14c5b52ba5ed38)).

### Changed

- **Each VM's proxy runs as two processes:** only `devvm _proxy` reads your Keychain, your agents' login files and your other files, and `devvm _proxy-child`, which reads the VM's network, holds only the values that the VM's own bindings name, and never a new login's tokens ([details](https://next.devvm.dev/docs/releases/0.2.0/#each-vms-proxy-runs-as-two-processes), [aeea313](https://github.com/devvmhq/devvm/commit/aeea3135b27e0de898a449adb63b7742126b8ddb)).
- **On macOS, the proxy's child runs in a macOS sandbox:** `devvm _proxy-child` starts under `sandbox-exec`, so a bug that a VM drove there couldn't read your files, reach the Keychain or connect to this machine's unix sockets ([details](https://next.devvm.dev/docs/releases/0.2.0/#the-childs-sandbox-on-macos), [941c63c](https://github.com/devvmhq/devvm/commit/941c63c696b2315329028049b21fa70cdb1b2a0d)).
- **On Linux, the proxy's child confines itself** with Landlock and a seccomp filter, so a bug that a VM drove there could read and write only its VM's logs and the shared Nix cache ([details](https://next.devvm.dev/docs/releases/0.2.0/#the-childs-sandbox-on-linux), [1793353](https://github.com/devvmhq/devvm/commit/1793353dd920a48cf4964b788a665c50cc208147)).
- **A proxy that can't get its whole sandbox keeps the VM's network, and `devvm doctor` warns** for each VM whose proxy runs that way, naming what the kernel lacks on Linux ([details](https://next.devvm.dev/docs/releases/0.2.0/#a-child-without-its-whole-sandbox), [941c63c](https://github.com/devvmhq/devvm/commit/941c63c696b2315329028049b21fa70cdb1b2a0d)).
- **The proxy's child connects only through `devvm _proxy`,** so a bug that a VM drove in the child can't reach this machine's services on `localhost`, its own addresses or your LAN's private addresses unless a rule names the address, just as the VM can't ([details](https://next.devvm.dev/docs/releases/0.2.0/#the-child-connects-only-through-devvm-_proxy), [3da3843](https://github.com/devvmhq/devvm/commit/3da38436a7f598dfe59711b0f64589e966bcb915)).
- **`devvm doctor` checks every VM's state:** it warns once of each VM whose state devvm can't read, naming the VM, the file and why, and it changes nothing ([details](https://next.devvm.dev/docs/releases/0.2.0/#devvm-doctor-checks-every-vms-state), [5924a37](https://github.com/devvmhq/devvm/commit/5924a373f07a6c550d9696d6332e546559d9650f)).
- **A marketplace's credential gets a warning:** `devvm agent import` and `devvm agent save` now warn when they copy a Claude Code marketplace with a password or an access token in it, because every VM with Claude Code can read it ([details](https://next.devvm.dev/docs/releases/0.2.0/#credentials-in-a-copied-marketplace), [c9d0fdb](https://github.com/devvmhq/devvm/commit/c9d0fdb270c3b348291d64333e12e4cef7856f07)).
- **`devvm agent import` has bounds:** an agent's folder that holds more than 20,000 files, folders and links, 128 MiB, or 16 MiB in one file fails the import before the store changes, naming the folder, so take out what it doesn't need and import again ([details](https://next.devvm.dev/docs/releases/0.2.0/#devvm-agent-imports-bounds), [c901b92](https://github.com/devvmhq/devvm/commit/c901b920efb08d6fdf2edbaa7cfd15b1941f83ab)).
- **A failed `devvm agent import` leaves the store as it was,** whether it fails while it reads or while it puts the settings and logins in place ([details](https://next.devvm.dev/docs/releases/0.2.0/#a-failed-import-changes-nothing), [3101c85](https://github.com/devvmhq/devvm/commit/3101c85260b2b5f872c0e85c0287d2d08e13bbe1)).
- **A project in an agent's folder gets a warning:** each launch of the VM and `devvm agent import` warn when a VM's project folder is inside a coding agent's folder on this machine, or holds one, because code in the VM can then change that agent's settings ([details](https://next.devvm.dev/docs/releases/0.2.0/#a-project-in-an-agents-folder), [c901b92](https://github.com/devvmhq/devvm/commit/c901b920efb08d6fdf2edbaa7cfd15b1941f83ab)).
- **`devvm agent import` follows no links while a VM's state can't be read:** it warns of each VM whose state it can't read, so run `devvm doctor` and import again ([details](https://next.devvm.dev/docs/releases/0.2.0/#an-import-while-a-vms-state-cant-be-read), [b04a1a9](https://github.com/devvmhq/devvm/commit/b04a1a9f1217cbf8069738b42d2072d4d84c53bd)).
- **Cursor's CLI in a VM can change less of your Cursor account:** its proxy refuses more of the methods that change your account, your team or your cloud agents, so do those from Cursor on your machine ([details](https://next.devvm.dev/docs/releases/0.2.0/#cursors-cli-and-your-cursor-account), [872c2e2](https://github.com/devvmhq/devvm/commit/872c2e23c0c4edc28d690ce13a028d6b8b140d31)).
- **Pins:** mise is 2026.11.10, in base and on this machine, the docker layer's Docker is 29.10.0 and its compose 5.8.0, and Cursor's CLI is 2026.11.17-f532c45, so base, every image built on it and every shared tool that mise installs are built again once ([details](https://next.devvm.dev/docs/releases/0.2.0/#pins), [c9005ae](https://github.com/devvmhq/devvm/commit/c9005ae4be13f6ebe337111bdba980c3f595c7fe), [01e837a](https://github.com/devvmhq/devvm/commit/01e837a164a2d751339e07197fe264b3e3804959)).
- **Slow steps show a status line:** in a terminal, devvm now shows what it's waiting for during its slow steps, such as finding the folder's VM, `devvm agent import` copying your agents' folders and every stop of a VM ([details](https://next.devvm.dev/docs/releases/0.2.0/#status-lines-for-slow-steps), [2b176c9](https://github.com/devvmhq/devvm/commit/2b176c92b3a4e44f83df5a94d8abc710ff5e8097)).
- **Waiting for another devvm shows a status line,** such as while another devvm changes the same VM's state, and only while it waits ([details](https://next.devvm.dev/docs/releases/0.2.0/#status-lines-while-devvm-waits), [cb7177b](https://github.com/devvmhq/devvm/commit/cb7177b32c3f40c38848c8c5740073e245f79eca)).

### Fixed

- **devvm says when it can't read a project folder:** it now names the folder and why it can't be read, where it used to say that the folder's VM was made for an earlier folder, so make the folder readable again ([details](https://next.devvm.dev/docs/releases/0.2.0/#a-project-folder-devvm-cant-read), [cb7177b](https://github.com/devvmhq/devvm/commit/cb7177b32c3f40c38848c8c5740073e245f79eca)).
- **A warning no longer lands on the status line:** a message now prints above the status line, and a question, the picker and an agent's login in the VM take the status line away until they're done, so its redraw no longer erases what you typed ([details](https://next.devvm.dev/docs/releases/0.2.0/#warnings-and-the-status-line), [2b176c9](https://github.com/devvmhq/devvm/commit/2b176c92b3a4e44f83df5a94d8abc710ff5e8097)).
- **`devvm agent login claude --setup-token` shows Claude Code's address:** when devvm runs in a terminal, an agent's login in the VM gets a terminal of its own, so Claude Code shows the address to open and the prompt for its code ([details](https://next.devvm.dev/docs/releases/0.2.0/#claude-codes-setup-token-login), [#57](https://github.com/devvmhq/devvm/issues/57), [6965efc](https://github.com/devvmhq/devvm/commit/6965efcc0a97f7f6334f00d0530007ecf459972c)).
- **Ctrl-C ends an agent's login in the VM,** in a terminal, and devvm puts the terminal back as it was before the login ([details](https://next.devvm.dev/docs/releases/0.2.0/#ctrl-c-in-an-agents-login), [6965efc](https://github.com/devvmhq/devvm/commit/6965efcc0a97f7f6334f00d0530007ecf459972c)).
- **The VM's shell gets your terminal's 24-bit color:** devvm's shell in a VM, `devvm agent login` and `ssh` to a VM by name now pass on your terminal's `COLORTERM` when it's `truecolor` or `24bit`, so programs in the VM no longer fall back to fewer colors ([details](https://next.devvm.dev/docs/releases/0.2.0/#24-bit-color-in-a-vm), [#54](https://github.com/devvmhq/devvm/issues/54), [947decb](https://github.com/devvmhq/devvm/commit/947decb301c609cb8eba59a92fa6fa2c373945a4)).
- **MCP servers' logins in a VM finish and stay:** with your subscription's login, devvm now replaces only the Claude login in the VM's `~/.claude/.credentials.json`, so the MCP servers' logins you make in a VM stay in that VM ([details](https://next.devvm.dev/docs/releases/0.2.0/#mcp-servers-logins), [#62](https://github.com/devvmhq/devvm/issues/62), [ea3037b](https://github.com/devvmhq/devvm/commit/ea3037bc157903525be51c83aedfd72c37da3cbb)).
- **Your claude.ai connectors work in a VM:** with your subscription's login, the VM's proxy now puts the login into the connectors' requests too, from each VM's next launch. Code in the VM can then read and act through your connectors, so disconnect the ones you don't want VMs to use, or deny `mcp-proxy.anthropic.com` with `devvm network deny` ([details](https://next.devvm.dev/docs/releases/0.2.0/#your-claudeai-connectors), [#61](https://github.com/devvmhq/devvm/issues/61), [c1db911](https://github.com/devvmhq/devvm/commit/c1db911d1ba3856299bd59b1c4d74620b7d49408)).
- **Claude Code's plugins work in a VM:** each VM's `~/.claude/plugins` is now its own folder, with the store's plugins as Claude Code's read-only seed, so a plugin's data, installing a plugin and updating a marketplace work in a VM ([details](https://next.devvm.dev/docs/releases/0.2.0/#claude-codes-plugins-in-a-vm), [#56](https://github.com/devvmhq/devvm/issues/56), [e97db05](https://github.com/devvmhq/devvm/commit/e97db057fd93873a14b075e7d46615dc2d020ac4)).
- **A project folder's VM works after your Mac restarts:** devvm no longer takes an unchanged folder for another one when a restart gives its disk another device number. A folder that moved after a restart, before its VM started again, isn't offered the VM, so `devvm adopt VM` moves it ([details](https://next.devvm.dev/docs/releases/0.2.0/#a-project-folder-after-your-mac-restarts), [#60](https://github.com/devvmhq/devvm/issues/60), [2c0a894](https://github.com/devvmhq/devvm/commit/2c0a894a1cb7347f3d6ebbcb3c39390d07ab4ed8)).
- **A folder that moved across a restart keeps its VM:** each VM now records its folder's volume, so devvm offers a folder that moved while a restart renumbered its disk the VM it had, where it used to make it a second VM ([details](https://next.devvm.dev/docs/releases/0.2.0/#a-folder-moved-across-a-restart), [ba510ee](https://github.com/devvmhq/devvm/commit/ba510eec1f55a7cd656050eabe14c5b52ba5ed38)).
- **A folder on another volume needs `devvm adopt`:** a folder at the VM's own path on another volume than the one recorded, such as a copy of the disk, or a Btrfs snapshot rolled back there on Linux, gets the VM only after `devvm adopt` ([details](https://next.devvm.dev/docs/releases/0.2.0/#a-folder-on-another-volume), [4ccdbf8](https://github.com/devvmhq/devvm/commit/4ccdbf8125fe4a655980e77a7454c209e98ada70)).
- **Two devvms no longer write the agent store at once:** `devvm agent import`, `devvm agent save` and a start that cleans the store now take turns, so a second one says it's waiting and goes on once the first is done ([details](https://next.devvm.dev/docs/releases/0.2.0/#two-devvms-at-the-agent-store), [b04a1a9](https://github.com/devvmhq/devvm/commit/b04a1a9f1217cbf8069738b42d2072d4d84c53bd)).
- **A failed `devvm agent save` leaves the store as it was,** because a save now saves all or nothing, as an import does ([details](https://next.devvm.dev/docs/releases/0.2.0/#a-failed-save-changes-nothing), [f80fd2d](https://github.com/devvmhq/devvm/commit/f80fd2df6031e1bb3ac86e5ec7d410cac0551104)).
- **`devvm agent save` and a VM's new Claude Code login take turns,** and Ctrl-C while the save waits ends the wait ([details](https://next.devvm.dev/docs/releases/0.2.0/#devvm-agent-save-and-a-new-claude-code-login), [f80fd2d](https://github.com/devvmhq/devvm/commit/f80fd2df6031e1bb3ac86e5ec7d410cac0551104)).

Thanks to @jspiro for the report and @dhruv1220 for the tests' idea in [#58](https://github.com/devvmhq/devvm/pull/58) ([details](https://next.devvm.dev/docs/releases/0.2.0/#names-you-choose-in-an-agents-settings), [#55](https://github.com/devvmhq/devvm/issues/55), [f384829](https://github.com/devvmhq/devvm/commit/f3848294d8e1095f115ae13e224697484b38c47c)).

## 0.1.0

Released 2026-11-06.

The first release of devvm, which gives each project folder an isolated VM of its own, ready for you or a coding agent to work in. It runs on macOS 13 or newer and on Linux, on arm64 and x86_64, with Lima 2.0 or newer. It's tested on Apple silicon Macs and on Linux on both arm64 and x86_64, but not yet on Intel Macs.

- **A VM for each project folder:** running `devvm` in a folder makes its VM, or opens the one it has, and gives you a shell in it at the same path as on your machine. The VM mounts only that folder read-write, and with `--clone` it gets a clone of the repo of its own instead, whose work you fetch with `git fetch devvm`.
- **Ready in seconds:** every VM is a copy of a base image that devvm builds once, and the toolchains and coding agents are shared tools that VMs mount read-only. devvm detects node, python, rust and go from the project's files, and the built-in `docker`, `nix` and `desktop` layers, your own layers from `devvm layer new`, a project's `devcontainer.json` and `--from` with a container image change what a VM starts from.
- **Coding agents in the sandbox:** Claude Code, Codex and opencode run in the VM with your settings, skills and MCP servers. devvm keeps their settings and logins in a store of its own on your machine, `devvm agent import` copies them in from an agent you already use, `devvm agent login` makes an agent's login from the VM, and `devvm agent save` brings a VM's settings back to the store after you review the diff.
- **Network tiers and secrets:** every VM goes through a proxy that devvm runs for it, and its tier, which is open, internet, allowlist or none, decides what the proxy lets it reach. New VMs get the allowlist tier. On every tier, your secrets, such as your GitHub token and Claude Code token, stay on your machine, because the proxy puts them into the VM's requests.
- **`.git` protection:** on macOS, devvm locks a project's git hooks and config with a flag that even root in the VM can't clear, so code in the VM can't make your next git command on this machine run something.
- **Reaching VMs:** each running VM can be reached by name from ssh and from editors such as VS Code (`devvm code`), with your SSH agent only when you allow it. A VM forwards the ports you ask for, `devvm link` lets one VM reach a service that another VM publishes, and `devvm desktop` opens a VM's desktop in Screen Sharing on macOS, or serves it to a VNC viewer of your own on Linux.
- **Managing VMs and space:** `devvm ls`, `devvm stop`, `devvm restart`, `devvm update` and `devvm rm` manage VMs, and `devvm images`, `devvm gc`, `devvm space` and `devvm retention` show and clean up the images, shared tools and exports devvm keeps. devvm never deletes a project VM on its own, because it may hold unsaved work.
- **Installing and upgrading:** install devvm with Homebrew (`brew trust --formula devvmhq/tap/devvm`, then `brew install devvmhq/tap/devvm`) or with the install script, which checks the release's minisign signature and checksum and asks before it installs what devvm needs, such as Lima. `devvm doctor` checks this machine, and `devvm upgrade` installs a newer release once it has checked the signature.
- **For scripts:** many commands take `--json`, and `--no-input` makes devvm fail where it would ask, naming the flag that answers the question.
